# M2 — Boot One System246 Game

Status: M2.1 reference and resource definition is complete; M2.2–M2.6 implementation has not started. [M1](M1.md) provides the required real, recoverable VM lifecycle.

## Goal

Reach the visible attract/demo checkpoint for NM00002, Bloody Roar 3, through the libretro Host, matching the standalone reference defined by the [baseline](baseline.md). Preserve System246 selection, CD media, `proverb.elf`, dongle and fighting JVS initialization through x6's existing `.acgame` path. BIOS screens, a boot logo, or ELF execution logs alone do not satisfy this milestone.

The reference checkpoint is the attract sequence's in-game presentation: a fighter on the 3D night rooftop stage, with the city skyline and moon in the background and no match HUD. The reference boot starts without an SRAM file, which the game initializes and x6 writes at shutdown.

## Writable-state contract

The planned locations extend M1's directory contract:

| Location | Role |
| --- | --- |
| `<system>/pcsx2x6/bios/` and `resources/` | Immutable BIOS inputs and matching runtime resources |
| `<save>/pcsx2x6/bios/` | BIOS working files, including same-stem companions and writable NVRAM |
| `<save>/pcsx2x6/memcards/` | Working dongle and optional save-card files |
| `<save>/pcsx2x6/arcade/<gameid>/sram.bin` | Per-game SRAM |

Resolve SRAM storage after x6 parses the manifest and before `ACSRAM::ReadFile()`, keeping the existing `VMBootParameters::filename` and `AutoDetectSource` path. The Host must not introduce a second manifest parser. Use a validated GameID as the initial save key, keep resolved write targets inside the save root, and reject source/destination aliases that could write back to original inputs.

An existing SRAM save takes precedence. Import the manifest's initial SRAM only when the destination is absent; a missing source permits a new blank save, while an unreadable or incomplete existing source must not be treated as absent. Failed import must not leave a partial destination for the next load. BIOS preparation continues to copy all missing same-stem companion files without replacing existing working state. The existing card contract is user-supplied working dongle and optional save-card files under `memcards/`; the core has no defined source location or original-copy management for them.

`ACSRAM::ReadFile()` currently opens with `"r+b"`, although it only reads. Change reads to `"rb"` so read-only initial data can be loaded; handle write access separately during persistence. Close the file on every return and retain write protection after a failed read of existing data. Reset per-session protection and comparison state deliberately. Keep these emulator fixes independently reviewable from libretro path adaptation.

Before M2.3, choose the storage interface. One candidate adds a dedicated optional arcade save-directory field to `VMBootParameters`, keeps manifest parsing in `AutoDetectSource`, and lets ACSRAM retain separate destination and initial-source paths for import-on-first-use. A focused Host path hook is the alternative. The existing `VMBootParameters::arcade` field does not define import semantics and must not be reused for this purpose.

x6's CI downloads the mutable `latest` release; the commit and asset digest above identify the archive used for M2. The resources directory is `<system>/pcsx2x6/resources/`.

NM00002 boots without patches. The selected archive contains `NM00002_42B47327.pnach`, matching the game's ELF CRC, with only the optional `Widescreen 16:9` and `No-Interlacing` groups. These groups are excluded from x6's automatic activation of named arcade patches. The reference disables both options and enables no patch by name, so neither group applies. The loader still opens the archive for NM00002, which exercises archive opening, release and reopening.

Other named arcade patch groups are enabled automatically unless explicitly disabled. NM00054's Region check bypass therefore needs no new core setting to enable it. Decide in M2.4 whether to cover archive lifecycle alone or also use NM00054 as a targeted patch-application check; neither choice requires a new per-game patch interface. Successful archive access by itself does not establish patch application.

The patch archive needs explicit ownership through the core lifecycle. `OpenPatchesZip()` currently reports success with a null archive if `zip_source_file_create` fails; a successful open registers another `atexit` callback each time. Treat source creation failure as failure, retain correct source ownership when `zip_open_from_source` fails, and remove the `atexit` registration when introducing active cleanup. Adding a close operation alongside those callbacks would permit repeated closes of the same cached pointer.

Release the archive after its last user, clear the handle, and permit reopening after failure, deinit/init and a resource-directory change. `Patch::UnloadPatches()` currently clears patch state without closing the archive. The existing archive-open warning uses a static one-shot flag; subsequent failures still need useful logs, and diagnostics must not depend on another on-screen warning.

Report missing required resources and invalid archives clearly. Optional patches need not become boot requirements. Existing diagnostic messages should be assessed against the reference rather than suppressed to produce an empty error log.

## Minimum presentation path

Prefer the existing `MTGS::SaveMemorySnapshot()` → `GSSaveSnapshotToMemory()` → `GSRenderer::SaveSnapshotToMemory()` path before adding renderer hooks. CPU submits readback through MTGS, GS owns texture access and download, and the frontend presents only a completed pixel buffer. Waits must not retain a session lock needed by CPU or GS work.

`VSyncStart()` calls `gsPostVsyncStart()` before `PollInputOnCPUThread()`, which reaches `PumpCPUThread()` through `Host::PumpMessagesOnCPUThread()`. The current frame's vsync is therefore already queued when the CPU reaches the gate. A snapshot submitted there follows that vsync in MTGS order and can capture the completed current frame. `RunFrame()` alone does not wait for GS completion; ordered snapshot submission and completion resolve this without requiring a one-frame delay. Keep M1's run-token protocol.

Before M2.5, choose between snapshotting directly in `PumpCPUThread()` before publishing the completed-frame counter, or issuing a separate blocking CPU request from the frontend each frame. The first candidate publishes session-owned pixels before `RunFrame()` returns and avoids the extra request. Both require correct buffer handoff and completion ordering; neither is selected yet.

Initially target a fixed 640×480, 4:3 canvas, updating both the current 640×448 AV geometry and placeholder storage. The download is RGBA8 with R,G,B,A bytes; little-endian XRGB8888 requires B,G,R,X bytes, so swap red and blue. Verify pitch, orientation and aspect handling, avoiding double aspect correction. Black output is allowed before the first valid image, but persistent readback failure must be diagnosed. Clear image state on failure, content close and deinit so a new session never presents a previous game's frame.

Synchronous snapshot allocation and GPU waits are acceptable for this checkpoint. Add a narrow GS hook only if a concrete limitation prevents use of the existing interface. Hardware-context sharing, asynchronous downloads and performance tuning remain later work.

| Stage | Decision |

| M2.3 | Keep user-managed working dongles, or define original-source metadata through the same startup mechanism; do not add a Host manifest parser |

| M2.5 | Capture at the CPU gate before frame acknowledgement, or use a separate frontend-issued blocking CPU request |

## Acceptance boundary

- The frontend displays the NM00002 attract/demo checkpoint, then closes normally. Logs identify the intended board, BIOS, GameID, ELF/CRC, media, dongle, JVS mode, GameDB settings and applied patches.
- Missing BIOS, ELF, dongle or media, and an unusable save directory produce actionable failures and permit a valid load in the same core context afterward.
- Original inputs remain unchanged. Working state persists at the documented locations; existing saves survive preparation, and incomplete or unreadable SRAM is protected. If the game does not change SRAM during the short boot check, use a controlled disposable-data check to establish write/reopen behavior.
- A valid patch archive is exercised, released and reopened; absent and invalid archives follow the defined resource contract.
- New frame buffers, file paths and archive ownership preserve M1's close, stop-without-further-`retro_run`, active deinit, same-DLL reinitialization and full module-unload guarantees. No stale pixels or resource handles survive their owner.

Stop after the visible checkpoint and normal shutdown. Keep timing, screenshots, file hashes and pass/fail records outside this repository. System256/HDD content supplies only targeted regression coverage when affected by a change.

M3 remains responsible for usable video/audio/input, pause/resume and reset. M2 does not establish broad compatibility or performance claims.
