# M2 — Boot One System246 Game

Status: M2.1–M2.6 are complete. NM00002 reaches its attract sequence in RetroArch and closes normally; the acceptance boundary below holds on the same build. [M1](M1.md) provides the required real, recoverable VM lifecycle.

## Goal

Reach the visible attract/demo checkpoint for NM00002, Bloody Roar 3, through the libretro Host, matching the standalone reference defined by the [baseline](baseline.md). Preserve System246 selection, CD media, `proverb.elf`, dongle and fighting JVS initialization through x6's existing `.acgame` path. BIOS screens, a boot logo, or ELF execution logs alone do not satisfy this milestone.

The reference checkpoint is the attract sequence's in-game presentation: a fighter on the 3D night rooftop stage, with the city skyline and moon in the background and no match HUD. The reference boot starts without an SRAM file, which the game initializes and x6 writes at shutdown.

## Writable-state contract

These locations extend M1's directory contract:

| Location | Role |
| --- | --- |
| `<system>/pcsx2x6/bios/` and `resources/` | Immutable BIOS inputs and matching runtime resources |
| `<save>/pcsx2x6/bios/` | BIOS working files, including same-stem companions and writable NVRAM |
| `<save>/pcsx2x6/memcards/` | Working dongle and optional save-card files |
| `<save>/pcsx2x6/arcade/<gameid>/sram.bin` | Per-game SRAM |

Preserve standalone x6's existing relative directory names through the shared `EmuFolders` defaults, while keeping immutable inputs in the system directory and writable state in the save directory. Existing names such as `bios`, `memcards`, `resources`, `cheats`, `patches`, `cache`, `textures`, `snaps` and `sstates` must not acquire core-specific aliases. Retain x6's native BIOS companion, card and SRAM file formats without adding a container or header. This is layout and data-format compatibility, not a complete user-directory mirror or a promise that every standalone feature is supported. The centralized `arcade/<gameid>/sram.bin` location is a core extension; standalone x6 derives SRAM from the content directory.

Resolve SRAM storage after x6 parses the manifest and before `ACSRAM::ReadFile()`, keeping the existing `VMBootParameters::filename` and `AutoDetectSource` path. The Host must not introduce a second manifest parser. The manifest's `sram=` value identifies only the initial source; if omitted, x6's default source name is `sram.bin` under the content subdirectory. The destination is always `<save>/pcsx2x6/arcade/<gameid>/sram.bin`, regardless of the source filename. The GameID is validated as `NM` followed by five digits, so it is a plain directory name below the save root. The game directory is created at startup. Startup fails with a specific error when it cannot be created, or when the destination directory or file is the same file-system object as the source directory or file, whether reached through links, a different case or relative components. There is no fallback to the content or working directory.

The initial save key is GameID alone. Content revisions or regional variants with the same GameID share one SRAM file, whose contents may be incompatible across variants. Variant isolation is not part of M2; this limitation applies even when their ELF CRCs or content filenames differ.

An existing SRAM save takes precedence. The manifest's initial SRAM is imported only when the destination is reported as absent; a missing source permits a new blank save. An unreadable or incomplete source keeps the session write-protected, so no destination is created and the import is retried on the next load. Imported data reaches the destination at the first save, which writes a new image to a temporary file and renames it into place, so a failed save leaves no partial destination. BIOS preparation continues to copy all missing same-stem companion files without replacing existing working state. The existing card contract is user-supplied working dongle and optional save-card files under `memcards/`; the core has no defined source location or original-copy management for them.

`ACSRAM::ReadFile()` reads without write access and closes the file on every path, so read-only initial data loads normally. Only an image the file system reports as absent starts blank; any other open failure, a read error, or an image shorter than 32 KiB keeps write protection for the session and leaves the image untouched. Reads and the unchanged-data check at save cover only the first 32 KiB. The image paths are reset before manifest parsing; protection and the buffer are reset when reading begins. On save, an existing image is updated in place and never recreated, so a file that cannot be opened for writing is not truncated. If the image cannot be opened for the unchanged-data check, saving is skipped unless the open explicitly reports it as absent. These emulator fixes stay independently reviewable from libretro path adaptation.

The Host passes `<save>/pcsx2x6/arcade` in the optional `VMBootParameters::arcade_save_directory` field. Manifest parsing stays in `AutoDetectSource`, and ACSRAM keeps separate save and initial-source paths. When the field is empty, x6 reads and saves the manifest's image in place as before. The existing `VMBootParameters::arcade` field does not define import semantics and is not reused. Dongle and save-card originals remain user-managed; the core uses the supplied working files without adding an original-copy mechanism.

x6's CI downloads the mutable `latest` release; the commit and asset digest above identify the archive used for M2. The resources directory is `<system>/pcsx2x6/resources/`.

NM00002 boots without patches. At the pinned x6 revision, arcade boots pass CRC 0 to the patch loader. Archive lookup uses exact names: `NM00002.pnach`, then `00000000.pnach`. The selected archive contains `NM00002_42B47327.pnach`, which is not read by that lookup; its optional patch groups are therefore not reached. The archive is still opened before entry lookup, so NM00002 exercises opening, release and reopening without applying a patch.

Retain the pinned archive and digest above. Its CRC-suffixed arcade entries are unused by this revision. The four entries it can match, `NM00045.pnach`, `NM00046.pnach`, `NM00053.pnach` and `NM00054.pnach`, are identical to those in the standalone reference archive.

Other named arcade patch groups are enabled automatically unless explicitly disabled. NM00054's Region check bypass serves as the targeted patch-application check in addition to NM00002's archive-lifecycle checks. No new per-game patch interface is needed. Successful archive access by itself does not establish patch application.

The patch archive is owned by each lookup. `Patch::OpenPatchesZip()` returns a managed archive that the lookup closes when it finishes, so there is no cached archive pointer, no `atexit` cleanup and no handle that outlives a session, a failed startup or a deinit. Each lookup resolves the archive from the current resources directory, so a failed open is retried and a resource-directory change takes effect on the next lookup. A failure to create the archive source counts as an open failure, and a source that cannot be opened as an archive is released. Entries read from the archive are closed after reading.

The archive-open warning is shown on screen once per module; every failed open is logged with the archive path and the libzip reason, which distinguishes a missing archive from a damaged one.

Report missing required resources and invalid archives clearly. Optional patches need not become boot requirements. Existing diagnostic messages should be assessed against the reference rather than suppressed to produce an empty error log.

## Minimum presentation path

The core uses the existing `MTGS::SaveMemorySnapshot()` → `GSSaveSnapshotToMemory()` → `GSRenderer::SaveSnapshotToMemory()` path without renderer hooks. CPU submits readback through MTGS, GS owns texture access and download, and the frontend presents only a completed pixel buffer. No wait retains a session lock needed by CPU or GS work.

`VSyncStart()` calls `gsPostVsyncStart()` before `PollInputOnCPUThread()`, which reaches `PumpCPUThread()` through `Host::PumpMessagesOnCPUThread()`. The current frame's vsync is therefore already queued when the CPU reaches the gate. A snapshot submitted there follows that vsync in MTGS order and can capture the completed current frame. The CPU thread waits for that snapshot before acknowledging the frame, so `RunFrame()` returns only after the current frame has been read back, without a one-frame delay. M1's run-token protocol is unchanged.

`PumpCPUThread()` captures the frame before publishing the completed-frame counter. The CPU thread runs the synchronous MTGS snapshot without the session lock, converts it to XRGB8888, exchanges it into the session's published frame under the lock, and only then acknowledges the frame. `RunFrame()` therefore returns with pixels ready, without a separate blocking CPU request each frame. Frames rotate through three buffers: the CPU thread's capture buffer, the published frame guarded by the session lock, and the frontend's presentation buffer, which `retro_run` exchanges with the published frame. The CPU thread never writes pixels that the video callback is reading.

Output is a fixed 640×480, 4:3 canvas; the snapshot fits the image into it with the GS aspect settings, and the frontend reports the same geometry with a 4:3 aspect ratio, so aspect correction is applied once. The download is RGBA8 with R,G,B,A bytes; the capture swaps red and blue for little-endian XRGB8888. Without a new frame, the frontend presents the session's previous frame; before the first frame it presents black. A run of 600 frames without an image is logged, as is the recovery. The published frame is cleared when a session starts and ends, and the frontend's buffer when content closes and at deinit, so a new session never presents a previous game's frame.

Synchronous snapshot allocation and GPU waits are acceptable for this checkpoint. Add a narrow GS hook only if a concrete limitation prevents use of the existing interface. Hardware-context sharing, asynchronous downloads and performance tuning remain later work.

## Acceptance boundary

- The frontend displays the NM00002 attract/demo checkpoint, then closes normally. Logs identify the intended board, BIOS, GameID, ELF/CRC, media, dongle, JVS mode, GameDB settings and applied patches.
- Missing BIOS, ELF, dongle or media, and an unusable save directory produce actionable failures and permit a valid load in the same core context afterward.
- Original inputs remain unchanged. Working state persists at the documented locations; existing saves survive preparation, and incomplete or unreadable SRAM is protected. If the game does not change SRAM during the short boot check, use a controlled disposable-data check to establish write/reopen behavior.
- A valid patch archive is exercised, released and reopened; absent and invalid archives follow the defined resource contract.
- New frame buffers, file paths and archive ownership preserve M1's close, stop-without-further-`retro_run`, active deinit, same-DLL reinitialization and full module-unload guarantees. No stale pixels or resource handles survive their owner.

Stop after the visible checkpoint and normal shutdown. Keep timing, screenshots, file hashes and pass/fail records outside this repository. System256/HDD content supplies only targeted regression coverage when affected by a change.

M3 remains responsible for usable video/audio/input, pause/resume and reset. M2 does not establish broad compatibility or performance claims.
