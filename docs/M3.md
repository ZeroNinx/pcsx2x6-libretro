# M3 — Basic Video, Audio, and Input

Status: M3.1–M3.6 are complete. [M2](M2.md) supplies the recoverable arcade VM and minimum video path.

## Goal and scope

Make NM00002 Bloody Roar 3 usable through RetroArch: a correctly described image, audible stereo output, two-player fighting JVS controls, reset, and safe pause/resume and content reuse. Preserve the selected standalone behavior and the system/save directory contract.

Retain the CPU worker, separate GS thread, Vulkan Surfaceless device and synchronous MTGS readback. Hardware-image delivery, GPU download optimization, border cropping and GS ownership changes remain separate work. M3.4a adds basic digital drum controls for NM00054. Savestates, rewind, runahead, netplay and other arcade peripherals are outside M3's acceptance boundary.

## Execution and callback contract

Normal execution follows this order:

1. The frontend polls input and publishes a complete snapshot with a frame request.
2. The CPU thread consumes that request and applies the snapshot before advancing emulation. Successful VM initialization stays parked until the first request.
3. At the next emulated vsync, the CPU thread submits ordered GS readback, completes the image and captures the audio boundary and current timing.
4. Completed-frame state is published before the frontend is notified. The CPU waits for the next request while still servicing commands and stop requests.
5. The frontend announces any AV changes, presents the completed image and submits only the audio belonging to that completion.

Frame requests and completions have an explicit sequence. A request must not both acknowledge one frame and authorize an unrequested next frame. Failed startup, reset, unload and reinitialization invalidate obsolete frame, input and audio state. No frontend callback runs on CPU, GS or an audio worker, and no GS wait holds the session lock. VM transitions remain CPU-thread operations.

The request/completion handshake keeps emulation parked between frontend requests while preserving GS queue ownership. Core boots set `VMBootParameters::start_unlimited=true`, selecting Unlimited mode and bypassing VM throttling. Device VSync stays disabled through `VsyncEnable=false`; RetroArch controls normal pacing and fast-forward.

Keep the existing wait diagnostics and rollback behavior. ## M3.2 — Video geometry and timing

- [x] Carry dimensions with each image instead of assuming every buffer is 640×480. Initially use the existing snapshot interface with zero requested dimensions and aspect correction disabled to obtain the current GS composite texture dimensions without the fixed-canvas rescale. Confirm the exact result before treating it as the output contract.
- [x] Keep output pixel dimensions separate from display aspect ratio. A composed texture may include upscaling or deinterlacing and is not necessarily the game's native framebuffer. Preserve the GS image, including existing borders; do not infer a crop from black pixels.
- [x] Retain XRGB8888 conversion and buffer ownership. Validate dimensions, pixel count, pitch and allocation limits; a missing first image produces black, and a later temporary failure may repeat only the current session's last valid frame.
- [x] Report the actual emulated vsync frequency, not internal game FPS or measured execution speed. Use `GetVerticalFrequency()` and the selected GS aspect policy through owned metadata; keep the nominal pre-boot values only until real timing exists.
- [x] Announce geometry/aspect-only changes with `RETRO_ENVIRONMENT_SET_GEOMETRY` when within the advertised maximum; use `SET_SYSTEM_AV_INFO` for timing, sample-rate or maximum-size changes. Make callbacks from the frontend before delivering the affected output and diagnose rejected required changes.

Relevant code: the session capture path, `pcsx2/MTGS.cpp`, `pcsx2/GS/Renderers/Common/GSRenderer.cpp`, and `pcsx2/GS.h`. Add a GS hook only for a demonstrated functional limitation of the existing interface.

The session submits one GS job per completed frame that takes the snapshot with zero requested dimensions, aspect correction and border cropping disabled, and reads the display aspect ratio. With the default zero crop, that snapshot is the composite texture at its own size: the PCRTC display resolution times the fixed upscale multiplier, after any deinterlacing. The aspect ratio comes from `GSGetDisplayAspectRatio()`, a GS-thread query of the aspect ratio setting and current video mode. It is the one emulator-side addition, because that policy and the progressive-mode state it depends on are private to the GS renderer.

The vsync frequency is `GetVerticalFrequency()` on the CPU thread. It is not published while the video mode is still uninitialized, because the emulator then only has a placeholder value. The frontend compares frame rates at single precision, the precision of the emulator's frame rate settings. Before it presents a frame, it announces a timing change with `SET_SYSTEM_AV_INFO`, and a size or aspect change alone with `SET_GEOMETRY`. The core keeps the AV information the frontend has accepted: it starts from the initial values when content loads or unloads, changes only when an update succeeds, and is what `retro_get_system_av_info` returns. A geometry update leaves the accepted timing unchanged. A rejected update is retried with later frames and logged once per distinct request; frames continue to carry their own size meanwhile.

## M3.3 — Audio delivery

- [x] Add a focused SPU2 output-stream factory or equivalent Host seam. The imported x6 revision has no `CustomOutputStreamFactory`; PCEE2's hook is a reference to adapt, not an existing interface. Preserve SPU2 mixing, volume and stream lifetime.
- [x] Use a stereo output path without opening a host audio device. Adapt `AudioStream` using `AudioSynchronizationMode::Disabled`; add only the access needed to drain actual buffered samples, avoiding underrun resampling caused by requesting samples that do not exist.
- [x] Use one core volume value to set both `SPU2/Output/StandardVolume` and `FastForwardVolume` explicitly in `ApplyCoreSettings()`, initially 100. Unlimited has target speed 0, so SPU2 selects its fast-forward volume when unmuted; setting only the standard volume would not control normal frontend-paced playback. Preserve mute behavior and verify the effective volume with a nondefault value. Stream-recreation coverage belongs to M3.5.
- [x] Convert the stream's floating-point stereo samples to interleaved signed 16-bit samples with clipping. Capture the committed-sample boundary at each completed vsync and transfer owned audio to the frontend. Account for the existing 64-frame SPU2 chunks and retain partial chunks across frame boundaries; do not invent a fixed 800-sample budget per frame.
- [x] Bound total frontend audio backlog to 250 ms at the active sample rate. Handle partial or zero acceptance from the batch callback without spinning, unbounded allocation, or consuming audio beyond the published boundary. On overflow, drop and count the oldest unaccepted frames so recovery does not replay an expanding delay; preserve the order of retained audio. Distinguish produced, accepted, retained and dropped frames.
- [x] Report the active stream sample rate. A rate change, accepted reset or new session must not mix old-rate audio with new output. Clear queues at lifecycle boundaries and release stream references before their VM owner is destroyed.
- [x] Submit audio only when its sample rate matches the frontend's accepted AV rate. A rejected rate change must not send new-rate samples to a device still configured for the old rate; retain or discard them with bounded storage and explicit accounting until the change is accepted.
- [x] Include audio discarded before frontend submission in the produced/dropped accounting, so produced equals accepted plus dropped plus queued even when unpublished audio changes sample rate.

Relevant code: `pcsx2/SPU2/spu2.{h,cpp}`, `pcsx2/Host/AudioStream.{h,cpp}`, and a separate frontend audio adapter under `libretro/`. Test with the actual sound of the selected title; nonzero buffers alone do not establish audible correctness.

With synchronization disabled, `OnTargetSpeedChanged()` clears the stream buffer and the partial SPU2 chunk. Do not change the VM limiter mode for frontend fast-forward; if a real target-speed transition occurs, account for that discarded stream data rather than filling an assumed per-frame sample budget. `GetNominalRate()` remains 1.0 when host-speed adjustment is inactive, and `SetTargetSpeed(0)` does not enable audio time stretching in Disabled mode. The adapter drains only committed samples.

The 250 ms limit is storage capacity, not a prefill requirement or a latency target.

`SPU2::SetOutputStreamFactory()` replaces the configured backend for every later output stream, and `AudioStream::GetBufferedFramesRelaxed()` is available to subclasses; these are the only emulator-side changes. The core installs a factory that creates a stereo `AudioStream` subclass with synchronization disabled, which opens no device. SPU2 creates, writes and destroys that stream on the CPU thread, and the session drains it there at each completed vsync, so the stream is observed without locking. A drain reads exactly the buffered frames, so the stream never pads with silence; SPU2 keeps its incomplete 64-frame chunk until it is committed. Samples are clipped and converted to signed 16 bits, and the audio up to a vsync is published with the frame that vsync completes.

The frontend appends each completion's audio to one queue and submits it through the batch callback until the frontend accepts nothing more; the rest waits for the next frame. Beyond 250 ms of queued audio, the oldest frames are dropped and counted, and one warning is logged per backlog. Audio of a different sample rate than the queued audio replaces it rather than mixing with it, and the stream's sample rate is part of the AV timing. Audio is submitted only while its sample rate is the rate the frontend has accepted; until a rate change is accepted, the queue keeps at most 250 ms of the new-rate audio and the hold is logged once. Audio discarded before reaching the queue counts as both produced and dropped. The queue is cleared when content loads and unloads; the counts of produced, accepted, dropped and still queued frames are logged then.

## M3.4 — JVS input

- [x] Register two joypad ports and frontend input descriptions. Poll only on the frontend thread; apply complete snapshots on the CPU thread using the frame contract from M3.1.
- [x] Reuse `ACJV::SetButtonState`, `InsertCoin` and current layout/binding metadata. Preserve x6's GameID-selected Bloody Roar layout and JVS protocol; avoid a second game-layout database or frontend writes into JVS globals.
- [x] Apply directions, Start and action buttons as levels. Coin is a rising-edge event per slot; Service remains an independent level control. Global Test toggles the existing Test Mode DIP once per press, following x6's DIP semantics.
- [x] Keep Test as an in-memory DIP: new content loads the configured default (off), while an ordinary reset preserves the current DIP state. `ApplySettings()` reloads DIP configuration through `ACJV::LoadConfig()`, including when reached by `UpdateDiscDetails()` or a game-settings reload. Avoid unnecessary whole-settings reloads during a session; do not use one to apply frontend-only frame or input changes.
- [x] Release controls on disconnect and content close. Reset/reconnect must not synthesize coin or Test events from a button already held; require release before rearming those edges. Frontend pause/resume must not duplicate an edge. Logical disconnect, reconnect, content reopening and pause are covered here; behavior across a reset is verified with M3.5.
- [x] Prevent disabled native SDL/DInput/XInput/RawInput sources from initializing or republishing input. Keep the change focused on respecting disabled sources and preserve independent source behavior for upstream comparison.

NM00002 mapping, confirmed by a short functional check:

| RetroPad control | JVS action |
| --- | --- |
| D-pad | Player directions |
| Y / B / A / X | Punch / Kick / Beast / Block |
| Start | Player Start |
| Select | Coin for that player's slot, on press |
| L3 | Player Service |
| Port 1 R3 | Global Test Mode toggle, on press |

Ports 1 and 2 use their corresponding player/coin slot; only port 1 owns the global Test action. Action positions follow x6's Bloody Roar defaults: Square / Cross / Circle / Triangle. M3.4a adds basic digital drum controls; full peripheral coverage remains later work.

The action buttons come from the running game's fighting or standard layout in ACJV: each layout button's JVS bit is driven by the RetroPad button at the PS2 pad position x6 assigns it (Square Y, Cross B, Circle A, Triangle X, L1/R1/L2/R2 the shoulder buttons). Directions, Start and Service use the fixed JVS bits. The CPU thread applies a frame's input snapshot before it advances that frame: levels through `ACJV::SetButtonState`, a coin through `ACJV::InsertCoin` and Test through `ACJV::ToggleDIPSwitchState`. A JVS bit is pressed while any button mapped to it is held, so a layout that wires actions onto the direction bits does not depend on mapping order. Coin and Test trigger on a press after the button has been seen released: a button already held when a session starts or a port reconnects does not trigger, and a button sampled as pressed before a pause does not trigger again when emulation resumes. Each session releases every mapped control before its first frame. Input descriptions are registered after content loads, with the layout's button names.

The core offers a RetroPad on both ports. When the frontend sets a port to no device through `retro_set_controller_port_device`, that port's controls are released and its edges wait for a release after it reconnects. Every device assignment is carried to the next frame's input, so a disconnect and reconnect between two frames also disarms the port's edges. A physical unplug that the frontend does not report cannot be distinguished from released buttons.

`InputManager::UpdateInputSourceState()` creates every source object but initializes a source only while it is enabled; previously it initialized a source the first time even when disabled and shut it down again.

## M3.4a — Basic digital drum input

Connect the existing `jvsmode=drum` path for NM00054 using the current per-frame input snapshot. Scope is two players' left/right Don (drum center) and left/right Ka (rim), four digital controls per player. Preserve x6's channel layout and pressed/released values; this step does not change input sampling or JVS timing.

Both ports use this RetroPad mapping:

| RetroPad control | Drum action |
| --- | --- |
| D-pad Left | Left Ka |
| D-pad Down | Left Don |
| B | Right Don |
| A | Right Ka |

In drum mode the D-pad does not drive JVS direction bits; Up and Right have no assigned game action. Coin, Start, Service and Test remain available. Other modes retain their direction mappings. Drum values remain `0xFFFF` while held and return to zero on release; whether a sustained value produces one or repeated hits is determined by the game.

- [x] Detect the active drum mode and use `ACJV::GetDrumBindings()` for the eight channel assignments. Apply explicit RetroPad mappings through `ACJV::SetDrumHit()` on the CPU thread and publish the corresponding input descriptions.
- [x] Use the mapping above without also writing JVS direction bits in drum mode. Preserve the existing Coin, Start, Service and Test controls. Clear drum channels at session boundaries and on logical disconnect, without changing fighting/standard mappings.
- [x] Check P1/P2 routing, individual presses, holds and releases, ordinary left/right alternation and simultaneous hits. Cover logical disconnect/reconnect and content reopening without stale drum input.
- [x] Use disposable saves for a short NM00054 check of menu/selection controls and Don/Ka recognition, then shut down normally. At normal frontend pacing, observe for at most 150 seconds (about 9000 frames) and stop as soon as the required behavior is confirmed. If no operable interface appears within that limit, record the reached checkpoint and shut down; controlled mapping checks can establish completion without reaching the menu. Recheck the affected NM00002 input and lifecycle behavior; reset coverage follows in M3.5.

Each session reads the drum mode from ACJV and assigns each of x6's drum bindings to a port by its player prefix and to a RetroPad button by its part name; a binding that matches no part is logged and stays unmapped. A drum game has no fighting or standard button layout, so B and A only hit the drum. Each session releases every JVS bit and all drum channels before its first frame, and a disconnected port releases its drum channels with its other levels. The input descriptions use the bindings' display names.

High-speed chart testing is performed by the user outside milestone acceptance. It is not required to complete M3.4a, M3 or proceed to later stages. Missed hits are tracked as [ISSUE-001](issues.md#issue-001-missed-drum-hits-in-fast-charts) and do not block project progress. Event buffering, sub-frame sampling, pulse shaping, velocity sensing and input-latency optimization require separate scope; ordinary mapping and lifecycle correctness remain required here.

## M3.5 — Pause, reset and reuse

- [x] Treat ordinary frontend pause as absence of frame requests: the CPU parks at its frame boundary and no new audio/video is submitted. Resume samples current input before advancing. libretro has no general `retro_pause` entry point; do not add an unnecessary public pause option.
- [x] Verify the existing CPU-thread pause/resume command path separately. If the VM is explicitly paused, a frame wait must finish without advancing the VM or hanging; stop and reset must remain serviceable.
- [x] Implement `retro_reset` through the CPU queue and `VMManager::RequestReset()`. Respect memory-card-busy refusal and the deferred `Resetting` path; do not acknowledge completion until the reset actually occurred, or discard output state when a reset was rejected. Preserve the prior running/paused intent.
- [x] Invalidate pre-reset pixels and audio, release held input including M3.4a's drum channels, and rearm edge controls safely. Preserve SRAM, BIOS working data and cards according to x6 semantics; reset is not a replacement content load or a save-file deletion.
- [x] Verify the effective audio volume after reset or another in-session stream recreation; the nondefault-volume creation check in M3.3 does not establish this behavior.
- [x] Check reset with Test Mode enabled: releasing the input trigger must not clear the DIP, and an ordinary reset must retain it. A new content session loads the default instead. If a reset explicitly reapplies settings, such as the upstream hardcore-mode transition, retain that configuration-reload behavior rather than promising unconditional DIP preservation.
- [x] Cover startup failure, close/reopen, active deinit and same-module deinit/init with the new media state. Stop and deinit must not require the frontend to accept more audio or call `retro_run` again.

The CPU thread runs the VM only on a frame grant: each frame request lets it run to the next vsync, so starting, resuming or resetting the VM never runs a frame nobody requested. While the VM is explicitly paused, frame requests complete without advancing it: the frontend presents the last frame again, submits no audio and holds audio queued from earlier frames until the VM runs again. Their input is not applied, but a device assignment made meanwhile reaches the next frame the VM runs, so a reconnect during the pause still disarms the port's edges. Stop and queued work are still served.

`retro_reset` queues the reset on the CPU thread and returns once it has happened or been refused. A running VM leaves execution through the deferred `Resetting` path before it resets; a paused VM resets at once and stays paused. A refused reset, such as while a memory card is being written, changes nothing. After a reset, audio committed since the last completed frame is discarded, no frame captured before the reset is presented, every control including the drum channels is released, and coin and Test wait for their buttons to be released. The frontend drops its queued audio and presents black until the reset VM completes an image. Coin counters and the Test DIP keep their values across a reset, as in x6; a new content session starts from the configured defaults. Reset does not read or write cards, SRAM or BIOS working data.

Arcade reset remains subject to [ISSUE-002](issues.md#issue-002-reset-failure-after-arcade-execution) and [ISSUE-003](issues.md#issue-003-excess-audio-after-resetting-a-running-vm). M3.5 acceptance covers the core's reset dispatch, refusal, completion acknowledgement and output/input cleanup; it does not establish that a running arcade title can resume successfully after reset or that post-reset SPU2 timing is correct. These issues are deferred independently of core integration. Close and reload content when a running title needs restarting. M3.6 carries these limitations forward.

## Functional reference for M4

M4 compares scheduling changes against this behavior:

| Area | Reference behavior |
| --- | --- |
| Rendering | Vulkan on a surfaceless device, separate GS thread, fixed upscale multiplier 1. Each completed frame is read back synchronously on the GS thread and converted to XRGB8888 on the CPU thread. |
| Frame progression | One frontend request runs the VM to its next vsync; the VM limiter is Unlimited and the frontend controls pacing and fast-forward. Input is applied on the CPU thread before the requested frame runs. |
| Geometry | The GS composite output at its own size, up to 1920×1080, with the display aspect ratio from the GS aspect setting and video mode. Borders are retained. Size and aspect changes use `SET_GEOMETRY`; timing changes use `SET_SYSTEM_AV_INFO`. |
| Timing | The emulated vsync frequency once a video mode is set; 59.94 Hz before that. |
| Audio | Interleaved signed 16-bit stereo at the active SPU2 stream rate, published with the frame whose vsync committed it. Frontend queue capacity is 250 ms; audio is submitted only at the accepted sample rate. |
| Input | Two RetroPad ports sampled once per frame. NM00002 fighting controls and NM00054 basic digital drums as described in M3.4 and M3.4a. Standard layouts share the mapping path but have only controlled bit-level coverage. Select coins, L3 Service, port 1 R3 toggles Test. |
| Lifecycle | Frontend pause stops frame requests; an explicitly paused VM completes requests without advancing. Reset, close/reopen and same-module reinitialization follow M3.5. |

Known limitations are listed in [Known Issues](issues.md): missed drum hits in fast charts, failure to continue after resetting a running arcade VM, and excess audio after such a reset. Border cropping, hardware image delivery, peripherals beyond fighting/standard buttons and digital drums, and savestates remain outside M3.
