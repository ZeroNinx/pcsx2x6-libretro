# M4 — Investigate Scheduling

Status: scope outlined; expand implementation TODOs after M3. Entry condition: [M3](M3.md) supplies a functional comparison baseline.

## Goal

Determine whether individual scheduling changes improve a defined workload while retaining lifecycle and observable behavior. Use paraLLEl-PS2 as a reference, not an automatic replacement.

## Planned work

- [ ] Map CPU/GS/MTVU ownership, queues, frame gates, backpressure, and queue draining in both designs.
- [ ] Explain progress during pause, startup, stop, context loss, and partial failure.
- [ ] Investigate sampling and input latching for [ISSUE-001](issues.md#issue-001-missed-drum-hits-in-fast-charts), using a repeatable input case before selecting changes.
- [ ] Define a short workload and comparison parameters, separating loading from active execution.
- [ ] Select one measured blocking or frame-delivery problem at a time.
- [ ] Document the rationale and acceptance condition for each experiment.
- [ ] Retain or reject each change using behavior and measurement evidence.

## Acceptance boundary

The project deliverable is the scheduling analysis and a justified decision for each proposed change. Keeping the original model is a valid result. CPU utilization alone does not establish an improvement. Existing correctness requirements cannot be postponed to this milestone.

Machine-specific timing data and raw traces remain in local records unless publication is explicitly requested. Accepted design decisions can be documented here without copying local test history.
