# M4 — Performance Optimization and Scheduling

Status: M4.1–M4.2 are complete; M4.3–M4.6 remain pending. [M3](M3.md#functional-reference-for-m4) supplies the accepted functional reference. Local measurement evidence is maintained outside this repository.

## Goal

Develop the working port into an efficient libretro core by reducing the computation, synchronization and data movement required for correct emulation. Audit paraLLEl-PS2 changes against their PCSX2 ancestry and the selected PCSX2x6 base, then evaluate configuration, execution and presentation costs while preserving M3 behavior. Measure throughput, frame-time tails and CPU/GPU work to improve real-time headroom on constrained hardware. Paced power measurements show the energy consequences of these costs; lower wattage is one possible benefit, not the sole acceptance target. Keeping the current model is valid when measurements do not justify a replacement.

Reference revisions remain those in [Baseline Definition](baseline.md#reference-revisions), including paraLLEl-PS2 `c8b51cfe0f63d87c58dae735dc64285e79fde76e`. The functional core implementation is `d8852c4`; `a28f337` records its M3 acceptance and comparison contract. paraLLEl-PS2 is a source reference, not a required build or an arcade performance baseline. Different emulation bases and renderers do not support direct frame-rate comparisons.

Use the v0.1 tag as the starting implementation for new performance experiments, preserving the earlier M3 DLL and M4.2 measurements as separate references. Freeze the v0.1 binary, effective settings, runtime system state and saves before comparing candidates.

Use the pinned PCSX2x6 revision when comparing upstream source. A newer checkout must be identified explicitly, with its differences accounted for; the working checkout name does not establish its revision. Preserve the accepted DLL and configuration outside the build directory before any new build or configure step.

## Preserved contract

- Normal execution advances one emulated vsync per frontend frame request. No frame runs between requests. An explicitly paused VM completes requests without execution, preserves queued audio, and carries device changes to the next executed frame.
- Input is applied before the authorized frame; pixels, timing and committed audio describe its completion. Callbacks remain on the frontend side. Any proposed pipelining must first define its frame/input/audio association and receive separate review.
- Preserve geometry/aspect reporting, accepted AV state, the active SPU2 sample rate, bounded 250 ms audio storage, and partial/zero acceptance behavior.
- Preserve CPU-thread VM ownership, command progress while parked, stop without another `retro_run`, and joined workers before module unload. A diagnostic timeout never authorizes abandoning a worker or unloading code it still executes.
- Keep renderer, emulation clocks, output quality, resources and writable-data handling fixed within a paired experiment, except for its one declared variable. Distinguish a configuration change from an implementation improvement. Hardware-image delivery needs a separate implementation plan; additional platforms, savestates and broad compatibility remain separate work.

[ISSUE-001](issues.md#issue-001-missed-drum-hits-in-fast-charts) is deferred behind performance work. Its input investigation and user-led high-speed chart tests are not prerequisites for M4.3–M4.6. Ordinary input correctness remains a regression requirement. The emulator-reset problems ISSUE-002 and ISSUE-003 remain deferred; M4 preserves the accepted reset dispatch/cleanup behavior without requiring their repair.

## M4.1 — Ownership and progress comparison

- [x] Map the core's frontend, CPU, GS and MTVU work when enabled: producers, consumers, shared state, publication, wakeups and completion conditions. Distinguish VU1's GIF data/completed-packet production from EE submissions to the MTGS command ring; do not infer a ring's writer count from the number of threads producing graphics data.
- [x] Record the effective `EmuCore/Speedhacks/vuThread` setting after settings and game overrides. Hardware-dependent defaults can enable MTVU and the Host does not override it, so it cannot be assumed identical across machines. Include VU1 packet completion, its queue and GS wakeups in the ownership graph when enabled.
- [x] Trace frame startup and steady state, input application, GS vsync submission, readback, audio publication and frontend callbacks. Distinguish command completion, ring emptiness and GPU completion.
- [x] Compare the paraLLEl-PS2 mechanisms below, including draining without presentation, pending frames, input latching and audio marks. Derive ownership from callers and producers, not from which thread opened GS.
- [x] Document progress and wakeups at first load, pause/resume, reset, stop, load failure and unload. Analyze graphics context callbacks only for designs that introduce frontend hardware-context ownership; they are not part of the current software-video handoff.

Source entry points for the comparison:

| Concern | Current core | paraLLEl-PS2 reference |
| --- | --- | --- |
| Frontend frame | `libretro/Libretro.cpp`, `libretro/LibretroSession.cpp` | `libretro/main.cpp`: `retro_run`, `MTGS::MainLoop(false)` |

**Deliverable:** a comparison with normal-frame and shutdown wait graphs, ownership invariants and a short list of testable hypotheses. Source-level similarity is not a measured benefit.

## M4.2 — Repeatable workload and measurement

- [x] Freeze the reference DLL, source/build identity, settings, resource identities and starting disk saves. Match and verify the effective MTVU setting in baseline and candidate runs; changing it is a separate experiment, not an incidental machine default. Use disposable save copies and replay the same boot/input sequence; there is no VM-savestate shortcut.
- [x] Define a 600-vsync NM00002 active-gameplay window after a fixed warm-up/checkpoint. The script must run through the entire measured interval: extend a separate benchmark copy if the M3 interaction script ends too early. Specify whether frame endpoints are inclusive and retain the same actions, stop point and cache policy on both sides. Separate startup, cache warm-up and loading from the measured interval.
- [x] Measure an unpaced harness for throughput and a normally paced frontend for frame-time variation. Use three paired baseline/candidate windows initially; add repetitions only to resolve a specific ambiguity. Do not replace measurements with a long gameplay run.
- [x] Collect frame request/return times, CPU gate waits, GS queue/backpressure waits, readback wait and conversion cost, and audio backlog/drops as relevant. Record median and tail frame times, total window time and instrumentation overhead. Do not add overlapping waits into a fictitious total or call CPU wait time GPU execution time.
- [x] Keep diagnostics aggregated or outside hot paths. Compare instrumented runs with an uninstrumented control before attributing a difference to scheduling.

**Deliverable:** a repeatable local workload and a bounded cost breakdown that identifies the first experiment. If no clear scheduling cost is exposed, record that result rather than choosing a replacement primitive anyway.

## M4.3 — LRPS2 change audit and performance baseline

- [ ] Identify the tested reference binary and effective options as well as the pinned source revision. Find the common PCSX2 ancestor and classify subsequent changes by host/pacing, renderer, synchronization, EE/IOP/VU execution, SPU2, storage, portability and correctness. Check whether equivalent behavior already exists in the selected x6 base; a textual delta or commit title alone does not establish an optimization.
- [ ] Build a short candidate list with public source/commit references, applicability to Windows x86-64, the executed path, prerequisites and affected correctness checks. Separate sustained-frame work from startup/reset/state-load costs, and exclude ARM-only or source-language changes as explanations for x86 performance or power without additional evidence.
- [ ] Verify effective MTVU/Instant VU1, wait-loop and interrupt-loop handling, fastmem, guest clocks, renderer/resolution, frame pacing, audio rate and frontend video settings. An arcade title and a console title do not define the same workload merely by sharing a series name or similar graphics.
- [ ] Define bounded real-time workloads: a repeatable NM00054 menu or ordinary-play interval for the reported use case, plus the established NM00002 interaction window where relevant. Use the same content, checkpoint and settings for the core's before/after comparison. LRPS2 provides reference behavior and hypotheses when identical content cannot run in both cores.
- [ ] Define the power metric: distinguish the configured TDP limit, measured APU package power and whole-device battery discharge. Keep display, refresh rate, audio, frontend pacing, cache warm-up and power policy comparable. Measure only the steady paced window; exclude boot, shader compilation and unpaced preparation.
- [ ] Establish both an unpaced throughput/frame-cost baseline and a normally paced work-cost baseline. Record median/tail frame times, missed frame budgets, delivered emulation progress, speed/audio correctness, process and per-thread CPU time, GPU activity and relevant memory/notification counts. Add measured power or energy per emulated second for handheld comparisons and power-related claims. Retain slow-state runs with an explicit label; use any state filter consistently and report what it excludes. The earlier fast-state-only throughput report does not establish a live-play energy baseline.

**Deliverable:** an applicable change inventory, a defined performance baseline and a ranked experiment list, with paced power evidence where relevant. Attribute costs across emulation, devices, synchronization and presentation before selecting an experiment; scheduling is not the assumed bottleneck. This stage does not promise parity with another core's wattage or require fixing high-speed drum input.

## M4.4 — Focused performance experiments

- [ ] Select one candidate from M4.3 and define its changed behavior, expected mechanism, performance metrics and relevant power evidence, correctness checks and rejection condition before editing code. A matched MTVU on/off comparison is a configuration experiment, not an automatic default change. Configuration and timer experiments are optional candidates, not prerequisites for investigating a demonstrated execution or presentation bottleneck.
- [ ] Prefer small, measurable changes first when applicable: unnecessary guest-loop execution, repeated hot-path work, notification frequency, or presentation copies. Replacing waits with spinning or changing a semaphore requires energy evidence and a sound sleep/wake protocol, even when a microbenchmark is faster.
- [ ] Evaluate one change at a time using the same baseline, starting system/save copies and paced workload. Measure uncapped throughput and frame-time tails separately from paced CPU/GPU work and power. Select acceptance metrics for the targeted bottleneck; a performance improvement need not demonstrate a wattage reduction to be retained. Preserve the frame/input/audio association, emulated clock rates and output quality; underclocking the guest or dropping output does not establish an equivalent optimization.
- [ ] Retain a change only when the claimed effect exceeds run-to-run variation and the affected correctness checks pass. Account for relevant trade-offs, including extra CPU work or power used to shorten a wait. A sound-related change needs PCM and IRQ timing coverage; a loop-skip change needs appropriate exception, side-effect and guest-progress checks. Revert unsupported or regressing experiments.
- [ ] Keep emulator fixes and frontend adaptations distinguishable. Larger recompiler or renderer changes receive their own scope; inventorying them here does not authorize bulk importing a fork.

**Deliverable:** a supported retain/reject decision for each selected experiment, identifying whether it reduces work, shortens the critical path, improves frame-time tails or lowers paced energy. Throughput gains do not imply energy savings, and power changes do not by themselves identify an emulation bottleneck.

## M4.5 — GS consumption and presentation decision

- [ ] Begin this assessment when M4.3 identifies relevant costs; unrelated M4.4 experiments need not finish first. Assess whether critical-path, CPU/GPU-work and relevant paced-power measurements justify moving GS consumption to the frontend side while retaining internal surfaceless Vulkan and CPU readback. Compare wait/ownership benefits with internal device/queue thread ownership, MTVU progress, command draining, pending frames and audio boundaries. Moving the consumer alone does not require RetroArch's hardware-render interface.
- [ ] Independently assess direct GPU-image delivery instead of CPU readback, including GPU-to-CPU transfer, CPU format conversion and frontend upload costs. This requires a frontend hardware-render interface and its context, synchronization and image-lifetime contract. It neither requires nor follows automatically from moving the GS consumer.
- [ ] Keep drain-only work distinct from frontend presentation. A pause/reset/stop path must not invoke video callbacks merely to unblock a producer; the proposed handling of a drained vsync and its audio must be explicit.
- [ ] For either justified change, write a separate implementation and validation plan before attempting it. Do not run the existing GS worker and a frontend consumer against the same ring. Scope hardware-context/image handoff separately from consumer migration.
- [ ] Otherwise retain the current architecture and document the measured reason. Eventcount/SPSC replacement, a new renderer or GPU-image sharing does not follow automatically from the reference implementation.

**Deliverable:** separate reviewed decisions on consumer placement and image delivery. Neither change is required to complete M4, and neither is a prerequisite for the other.

## M4.6 — Regression, performance conclusions and M5 handoff

- [ ] On one final uninstrumented build, run the affected M3 checks: NM00002 ordinary interaction, geometry/aspect and AV changes, audio counts/backpressure, P1/P2 routing, Coin/Service/Test, and basic NM00054 drum input.
- [ ] Cover no-request parking, first-frame stop, explicit pause with queued audio and device changes, reset dispatch/cleanup, close/reopen, active deinit and same-module reinitialization. Reuse bounded reset cases that avoid ISSUE-002; fault injection is repeated only when its paths changed.
- [ ] Verify writable-state isolation and baseline/candidate frame/audio association. Compare stable scripted checkpoints; a screenshot difference needs interpretation and does not by itself establish a regression or a gain.
- [ ] Repeat the affected throughput, frame-time and paced-work comparisons on the final build, plus power comparisons for related claims or trade-offs. Report their scope and variability alongside real-time correctness. Summarize retained and rejected changes, measurement limits, current ownership and unresolved issues. Preserve the functional reference and move remaining optimization, compatibility and upstream fixes to separately scoped work.
- [ ] Confirm M4 completion before entering M5. Keep source imports/upstream updates separate from scheduling changes and preserve all imported license notices.

## Acceptance boundary

M4 delivers the ownership/progress analysis, repeatable performance workloads, the LRPS2 applicability audit, decisions for selected experiments and the affected final regressions. Claimed benefits must exceed measurement variation and preserve emulation behavior and output quality. Power is an important constraint and diagnostic on handhelds, not a mandatory improvement for every accepted optimization. Measured power is required for energy claims and for evaluating changes to spinning, wakeups or idle behavior. Input investigation is deferred and ISSUE-001 may remain unresolved. Keeping the current model or making no optimization change are valid outcomes when the evidence supports them. Newly introduced correctness regressions are not deferred as optimization work. CPU utilization, average frame rate and power-limit settings alone do not establish energy savings or end-to-end input latency. Do not infer a linear wattage reduction from time spent waiting for a GPU fence.

Machine-specific timing data and raw traces remain in local records unless publication is explicitly requested. Accepted design decisions can be documented here without copying local test history.
