# M4 — Performance Optimization and Scheduling

Status: complete for the selected experiments. The H1 GPU-image implementation at `d477509` with an independent GS worker is the retained design and the accepted functional baseline for RetroArch, preserving the [M3 contract](M3.md#functional-reference-for-m4). Reinitialization within a resident core module and direct deinitialization of an active VM remain unverified on this hardware-video path. M4 does not establish that further optimization is exhausted. Local measurement evidence is maintained outside this repository.

## Goal

Develop the working port into an efficient libretro core by reducing the computation, synchronization and data movement required for correct emulation. Audit paraLLEl-PS2 changes against their PCSX2 ancestry and the selected PCSX2x6 base, then evaluate configuration, execution and presentation costs while preserving M3 behavior. Measure throughput, frame-time tails and CPU/GPU work to improve real-time headroom on constrained hardware. Paced power measurements show the energy consequences of these costs; lower wattage is one possible benefit, not the sole acceptance target. Keeping the current model is valid when measurements do not justify a replacement.

Reference revisions remain those in [Baseline Definition](baseline.md#reference-revisions), including paraLLEl-PS2 `c8b51cfe0f63d87c58dae735dc64285e79fde76e`. The M3 functional reference is `d8852c4`; `a28f337` records its acceptance and comparison contract. paraLLEl-PS2 is a source reference, not a required build or an arcade performance baseline. Different emulation bases and renderers do not support direct frame-rate comparisons.

Preserve v0.1 as the original performance reference, with the earlier M3 DLL and M4.2 measurements kept separately. Earlier H1 measurements used `70f3b46`; subsequent single-variable experiments should identify their starting revision and binary explicitly, including effective settings, runtime system state, saves and limitations. The accepted H1 functional baseline is `d477509`; earlier binaries retain their own measurement identities.

H1 retains the CPU frame-request protocol and independent GS worker, but replaces ordinary display readback, CPU pixel conversion and software upload with GPU-image delivery on a shared Vulkan device. It requires Vulkan context negotiation v2 and has no software-video fallback. Cached video-driver recreation preserves the session when the device and graphics queue remain compatible. Recovery onto another device or queue remains unsupported; see [ISSUE-004](issues.md#issue-004-video-driver-recreation-on-another-device-or-queue-ends-the-content-session). A shorter display critical path does not by itself establish reduced CPU work or power.

Use the pinned PCSX2x6 revision when comparing upstream source. A newer checkout must be identified explicitly, with its differences accounted for; the working checkout name does not establish its revision. Preserve the accepted DLL and configuration outside the build directory before any new build or configure step.

## Preserved contract

- Normal execution advances one emulated vsync per frontend frame request. No frame runs between requests. An explicitly paused VM completes requests without execution, preserves queued audio, and carries device changes to the next executed frame.
- Input is applied before the authorized frame; pixels, timing and committed audio describe its completion. Callbacks remain on the frontend side. Any proposed pipelining must first define its frame/input/audio association and receive separate review.
- Preserve geometry/aspect reporting, accepted AV state, the active SPU2 sample rate, bounded 250 ms audio storage, and partial/zero acceptance behavior.
- Preserve CPU-thread VM ownership, command progress while parked, stop without another `retro_run`, and joined workers before module unload. A diagnostic timeout never authorizes abandoning a worker or unloading code it still executes.
- Keep renderer, emulation clocks, output quality, resources and writable-data handling fixed within a paired experiment, except for its one declared variable. Distinguish a configuration change from an implementation improvement. Further presentation changes need their own plan; additional platforms, savestates and broad compatibility remain separate work.

[ISSUE-001](issues.md#issue-001-missed-drum-hits-in-fast-charts) is deferred behind performance work. Its input investigation and user-led high-speed chart tests are not prerequisites for M4.3–M4.6. Ordinary input correctness remains a regression requirement. The emulator-reset problems ISSUE-002 and ISSUE-003 remain deferred; M4 preserves the accepted reset dispatch/cleanup behavior without requiring their repair.

## M4.3 — LRPS2 change audit and performance baseline

- [x] Fix the retained H1 build and configuration for experiments, keeping the v0.1 and M4.2 references. Measurements use RetroArch with Vulkan v2 negotiation, a frozen start state, a fixed emulated clock, scripted input through the normal input path and per-thread cycle counts per emulated second.
- [x] Audit paraLLEl-PS2 changes since the common PCSX2 ancestor and list the candidates that apply to Windows x86-64: MTVU policy, the core's timer-resolution request, SPU2 IRQ comparison gating, EE wait-loop detection, VIF notification, wait primitives and frontend-side GS consumption.
- [x] Define bounded NM00054 windows (attract and in-song) and attribute their cost across the EE, GS, MTVU and frontend threads, the GS draw path and SPU2 mixing. An identical-console-content comparison with paraLLEl-PS2 was not built; it would require separately scoped console boot, BIOS, controller and memory-card support. Different-content measurements are treated as hypotheses, not as attribution.

## M4.4 — Focused performance experiments

Each experiment changed one variable against the same baseline, start state and workload, and was decided against run-to-run variation.

| Experiment | Decision |
| --- | --- |
| SPU2 volume-slide call-site check | Not retained; no repeatable gain |
| Link-time optimization of the emulation library | Not adopted; no repeatable gain |
| MTVU disabled | Not adopted; no repeatable benefit on the target workload, the default is kept |
| Core timer-resolution request removed | Not concluded; another 1 ms request remained active in the test environment, so the effect was not isolated |
| SPU2 IRQ comparison gating | Not built; IRQs were never enabled in the examined windows and mixing almost always runs one sample per batch, leaving no meaningful target |
| EE wait-loop detection extension | Not built; the hot self-looping blocks in the examined windows write memory and cannot be skipped |
| VIF notification deferral, wait-primitive replacement | Not pursued; no measured notification or wakeup cost |

## M4.5 — GS consumption and presentation decision

- [x] Retain H1 direct GPU-image delivery instead of ordinary CPU readback, conversion and frontend upload. It uses Vulkan v2 negotiation, shared-device queue synchronization and per-sync-index output images, with no software fallback.
- [x] Retain the independent GS worker. A prototype that consumed the GS command ring on the frontend thread kept the frame-request, output and audio contracts and passed lifecycle checks. It reduced CPU work and frame time slightly but raised power in the target handheld workload, so it is not adopted.
- [x] Keep drain-only work distinct from presentation: pause, reset and stop never call the video callback to unblock a producer.

## M4.6 — Regression, conclusions and M5 handoff

- [x] The final build is the accepted functional baseline `d477509`; M4 adds no further code change. Uninstrumented checks cover startup, dynamic AV information, cached-context fullscreen switching and close/reopen of NM00002, NM00054 and NM00002 within one frontend process. Controlled builds with the same functional source cover two-player fighting and drum input against v0.1 in the same frontend, writable-state isolation, running and paused reset, explicit pause, running exit, AV rejection and audio backpressure. Reset checks retain the limited acceptance boundary for ISSUE-002 and ISSUE-003.
- [x] The input mapping and audio adapter modules are unchanged since the M3 reference, so its Coin, Service and Test coverage remains applicable. H1's session and AV lifecycle changes are covered separately by the H1 regression.
- [ ] Reinitialization within a resident core module and direct deinitialization of an active VM remain unverified on the hardware-video path.

Remaining candidates move to separately scoped work: reducing GS draw, texture-cache and driver-command work, and isolating the effect of the timer-resolution request. RTSS frame limiting remains a known issue with a workaround ([ISSUE-005](issues.md#issue-005-higher-cpu-power-with-rtss-frame-limiting)).

## Acceptance boundary

M4 delivers the ownership/progress analysis, repeatable performance workloads, the LRPS2 applicability audit, decisions for selected experiments and the affected final regressions. Claimed benefits must exceed measurement variation and preserve emulation behavior and output quality. Power is an important constraint and diagnostic on handhelds, not a mandatory improvement for every accepted optimization. Measured power is required for energy claims and for evaluating changes to spinning, wakeups or idle behavior. Input investigation is deferred and ISSUE-001 may remain unresolved. Keeping the current model or making no optimization change are valid outcomes when the evidence supports them. Newly introduced correctness regressions are not deferred as optimization work. CPU utilization, average frame rate and power-limit settings alone do not establish energy savings or end-to-end input latency. Do not infer a linear wattage reduction from time spent waiting for a GPU fence.

Machine-specific timing data and raw traces remain in local records unless publication is explicitly requested. Accepted design decisions can be documented here without copying local test history.
