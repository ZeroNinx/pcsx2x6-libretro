# M4 — Investigate Scheduling

Status: planning complete; M4.1–M4.6 have not started. [M3](M3.md#functional-reference-for-m4) supplies the accepted functional reference.

## Goal

Identify the waits and ownership choices that limit a defined workload, compare them with paraLLEl-PS2, and evaluate focused changes while preserving M3 behavior. Keeping the current model is a valid result when measurements do not justify a replacement.

Reference revisions remain those in [Baseline Definition](baseline.md#reference-revisions), including paraLLEl-PS2 `c8b51cfe0f63d87c58dae735dc64285e79fde76e`. The functional core implementation is `d8852c4`; `a28f337` records its M3 acceptance and comparison contract. paraLLEl-PS2 is a source reference, not a required build or an arcade performance baseline. Different emulation bases and renderers do not support direct frame-rate comparisons.

Use the pinned PCSX2x6 revision when comparing upstream source. A newer checkout must be identified explicitly, with its differences accounted for; the working checkout name does not establish its revision. Preserve the accepted DLL and configuration outside the build directory before any new build or configure step.

## Preserved contract

- Normal execution advances one emulated vsync per frontend frame request. No frame runs between requests. An explicitly paused VM completes requests without execution, preserves queued audio, and carries device changes to the next executed frame.
- Input is applied before the authorized frame; pixels, timing and committed audio describe its completion. Callbacks remain on the frontend side. Any proposed pipelining must first define its frame/input/audio association and receive separate review.
- Preserve geometry/aspect reporting, accepted AV state, the active SPU2 sample rate, bounded 250 ms audio storage, and partial/zero acceptance behavior.
- Preserve CPU-thread VM ownership, command progress while parked, stop without another `retro_run`, and joined workers before module unload. A diagnostic timeout never authorizes abandoning a worker or unloading code it still executes.
- Keep the selected Vulkan backend, emulation settings, resources and writable-data contract fixed during a scheduling comparison. Hardware-image delivery, additional backends/platforms, savestates and broad compatibility are separate work.

[ISSUE-001](issues.md#issue-001-missed-drum-hits-in-fast-charts) is investigated without assuming a scheduling cause. High-speed chart tests remain user-led and non-blocking. The emulator-reset problems ISSUE-002 and ISSUE-003 remain deferred; M4 preserves the accepted reset dispatch/cleanup behavior without requiring their repair.

## M4.1 — Ownership and progress comparison

- [ ] Map the core's frontend, CPU, GS and MTVU work when enabled: producers, consumers, shared state, publication, wakeups and completion conditions. Distinguish VU1's GIF data/completed-packet production from EE submissions to the MTGS command ring; do not infer a ring's writer count from the number of threads producing graphics data.
- [ ] Record the effective `EmuCore/Speedhacks/vuThread` setting after settings and game overrides. Hardware-dependent defaults can enable MTVU and the Host does not override it, so it cannot be assumed identical across machines. Include VU1 packet completion, its queue and GS wakeups in the ownership graph when enabled.
- [ ] Trace frame startup and steady state, input application, GS vsync submission, readback, audio publication and frontend callbacks. Distinguish command completion, ring emptiness and GPU completion.
- [ ] Compare the paraLLEl-PS2 mechanisms below, including draining without presentation, pending frames, input latching and audio marks. Derive ownership from callers and producers, not from which thread opened GS.
- [ ] Document progress and wakeups at first load, pause/resume, reset, stop, load failure and unload. Analyze graphics context callbacks only for designs that introduce frontend hardware-context ownership; they are not part of the current software-video handoff.

Source entry points for the comparison:

| Concern | Current core | paraLLEl-PS2 reference |
| --- | --- | --- |
| Frontend frame | `libretro/Libretro.cpp`, `libretro/LibretroSession.cpp` | `libretro/main.cpp`: `retro_run`, `MTGS::MainLoop(false)` |
| Frame gate and input | Session requests, `LibretroInput`, `Counters.cpp` vsync pump | `MTGS.cpp` frame gate, `MTGSOwner.h`, `PAD.cpp` staged/live input |
| GS consumption | Separate worker, `MTGS::WaitGS`, ordered `CaptureFrame` readback | Frontend-side consumption, `WaitGS` producer distinction, pending drained vsync |
| Worker signaling | Session condition variable, MTGS/MTVU synchronization | `WorkEventCount.h`, eventcount signaling and producer/consumer publication |
| Audio boundary | `LibretroAudio::DrainCommitted` at completed vsync | `libretro/audio_queue.*`, vsync audio marks and presented-frame upload |

**Deliverable:** a comparison with normal-frame and shutdown wait graphs, ownership invariants and a short list of testable hypotheses. Source-level similarity is not a measured benefit.

## M4.2 — Repeatable workload and measurement

- [ ] Freeze the reference DLL, source/build identity, settings, resource identities and starting disk saves. Match and verify the effective MTVU setting in baseline and candidate runs; changing it is a separate experiment, not an incidental machine default. Use disposable save copies and replay the same boot/input sequence; there is no VM-savestate shortcut.
- [ ] Define a 600-vsync NM00002 active-gameplay window after a fixed warm-up/checkpoint. The script must run through the entire measured interval: extend a separate benchmark copy if the M3 interaction script ends too early. Specify whether frame endpoints are inclusive and retain the same actions, stop point and cache policy on both sides. Separate startup, cache warm-up and loading from the measured interval.
- [ ] Measure an unpaced harness for throughput and a normally paced frontend for frame-time variation. Use three paired baseline/candidate windows initially; add repetitions only to resolve a specific ambiguity. Do not replace measurements with a long gameplay run.
- [ ] Collect frame request/return times, CPU gate waits, GS queue/backpressure waits, readback wait and conversion cost, and audio backlog/drops as relevant. Record median and tail frame times, total window time and instrumentation overhead. Do not add overlapping waits into a fictitious total or call CPU wait time GPU execution time.
- [ ] Keep diagnostics aggregated or outside hot paths. Compare instrumented runs with an uninstrumented control before attributing a difference to scheduling.

**Deliverable:** a repeatable local workload and a bounded cost breakdown that identifies the first experiment. If no clear scheduling cost is exposed, record that result rather than choosing a replacement primitive anyway.

## M4.3 — Input sampling and missed-hit investigation

- [ ] Compare when the frontend samples, when the CPU consumes the snapshot and when JVS reads each drum channel; contrast this with paraLLEl-PS2's staged/live PAD input without assuming its console devices implement x6's JVS semantics.
- [ ] Trace a short deterministic sequence of presses, releases, alternation, simultaneous hits and logical reconnects. Relate each transition to request/vsync/JVS-read boundaries. Distinguish transitions visible to the core from physical events the frontend never sampled.
- [ ] Use user-provided high-speed reproduction details when available. If the problem is not localized, retain ISSUE-001 and continue M4; neither an unavailable test nor an unresolved missed hit blocks later steps.
- [ ] Propose a focused input fix only after localization, with its own ordinary-input and user-reproduction checks. Preserve x6's drum levels unless a demonstrated fault justifies a semantic change.

**Deliverable:** an input timeline and an evidence-based conclusion, which may remain unresolved. Event queues, sub-frame polling and pulse shaping are not default implementations.

## M4.4 — Focused synchronization experiments

- [ ] Select one measured hypothesis from M4.2. Define the changed ownership/wait condition, expected benefit, affected checks and rejection condition before editing code.
- [ ] Prefer changes that retain the separate GS consumer first: demonstrated duplicate waits, unnecessary synchronization, or costly work notification/backpressure. Primitive replacement requires evidence of that primitive's cost and a correct platform fallback.
- [ ] Evaluate one change at a time using the same workload, source baseline, starting saves and instrumentation. Check both normal pacing and unpaced throughput; an average gain alone does not justify worse frame tails or broken frame association.
- [ ] Retain a change only when the effect exceeds observed run-to-run variation and the affected correctness checks pass. Revert unsupported/regressing experiments and record the decision locally.

**Deliverable:** a decision for each selected experiment. There is no minimum number of code changes or preset speedup target.

## M4.5 — GS consumption and presentation decision

- [ ] Assess whether measurements justify moving GS consumption to the frontend side. Compare possible wait/ownership benefits with context ownership, MTVU progress, command draining, pending-frame storage and audio-mark requirements.
- [ ] Keep drain-only work distinct from frontend presentation. A pause/reset/stop path must not invoke video callbacks merely to unblock a producer; the proposed handling of a drained vsync and its audio must be explicit.
- [ ] If migration is justified, write a separate implementation and validation plan before attempting it. Do not run the existing GS worker and a frontend consumer against the same ring. Any required hardware-context/image handoff gets separate scope.
- [ ] Otherwise retain the current architecture and document the measured reason. Eventcount/SPSC replacement, a new renderer or GPU-image sharing does not follow automatically from the reference implementation.

**Deliverable:** a reviewed architecture decision. A full frontend-owned GS migration is not required to complete M4.

## M4.6 — Regression, conclusions and M5 handoff

- [ ] On one final uninstrumented build, run the affected M3 checks: NM00002 ordinary interaction, geometry/aspect and AV changes, audio counts/backpressure, P1/P2 routing, Coin/Service/Test, and basic NM00054 drum input.
- [ ] Cover no-request parking, first-frame stop, explicit pause with queued audio and device changes, reset dispatch/cleanup, close/reopen, active deinit and same-module reinitialization. Reuse bounded reset cases that avoid ISSUE-002; fault injection is repeated only when its paths changed.
- [ ] Verify writable-state isolation and baseline/candidate frame/audio association. Compare stable scripted checkpoints; a screenshot difference needs interpretation and does not by itself establish a regression or a gain.
- [ ] Summarize retained and rejected changes, measurement limits, current ownership and unresolved issues. Preserve the functional reference and move remaining optimization, compatibility and upstream fixes to separately scoped work.
- [ ] Confirm M4 completion before entering M5. Keep source imports/upstream updates separate from scheduling changes and preserve all imported license notices.

## Acceptance boundary

M4 delivers the ownership/progress analysis, a repeatable measured workload, the input investigation, decisions for selected experiments and the affected final regressions. Keeping the current model, making no optimization change, or leaving ISSUE-001 unresolved are valid outcomes when the evidence supports them. Newly introduced correctness regressions are not deferred as optimization work. CPU utilization and average frame rate alone do not establish success or end-to-end input latency.

Machine-specific timing data and raw traces remain in local records unless publication is explicitly requested. Accepted design decisions can be documented here without copying local test history.
