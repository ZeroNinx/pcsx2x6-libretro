# M5 — Core Features and Compatibility

Status: M5.1 capability audit and save-state design, M5.2 core options and localization, and the selected M5.3 input-validation scope are complete. Standard-layout real-game coverage remains unavailable. M5.4 in-memory save states, the M5.5 lifecycle scope and the M5.5a Direct3D 11 renderer are complete as described below. The core delivers GPU images directly and keeps an independent GS worker. Vulkan (default) requires context negotiation v2; Direct3D 11 requires a frontend D3D11 driver. There is no software-video fallback.

## Goal and priorities

Complete the everyday libretro core experience: truthful capability information, save states, useful and localized core options, reliable input, and predictable lifecycle and persistent storage. Preserve the accepted frame/input/audio contract and keep emulation fixes distinct from frontend integration.

The original performance, board/media, platform, VFS and peripheral candidates remain available, but do not all become requirements for M5. Core features take priority. Additional renderer/backend support is selected for M5.5a, with its option contract prepared in M5.2; other original candidates remain individually scoped. Each implementation step receives a bounded design and acceptance case before code changes; the outline below does not authorize bulk porting reference implementations.

## M5.1 — Capability and state-completeness audit

- [x] Inventory implemented, missing and conditional libretro capabilities against the exported callbacks, core-info file, README and package. Correct contradictory capability descriptions when implementing the inventory changes.
- [x] Audit the existing state entries and their restore paths: CPU/IOP/VU, GS, SPU2, arcade RAM/SRAM, JVS/UART, ATA/ATAPI and media position, timers/interrupts, cards, BIOS-side state and integration-owned state. Identify omitted mutable state and how each item is restored or deliberately external to a snapshot.
- [x] Define the first save-state support boundary, format/version and content/configuration identity checks, memory budget, stable serialization size policy and CPU/GS/MTVU quiescence protocol. Decide how restoring in-memory saves interacts with later disk persistence before implementation.

The current libretro serialization callbacks are stubs. The emulator already has ACRAM, SRAM and JVS state entries, but its JVS entry stores coin counts only; existing state functions do not establish complete arcade-device coverage. Reuse valid components rather than treating a wrapper around the desktop file-save API as sufficient.

The initial target is loading within the same build, content and compatible configuration, including after closing and reopening content. A same-session-only restriction requires an explicit scope review. Define refusal conditions during startup, shutdown and unsafe card/media writes.

**Deliverable:** a capability matrix and the save-state design below, with explicit gaps and acceptance cases. Implementation and runtime acceptance remain in M5.4. Unresolved state completeness blocks advertising save states, not unrelated option or input work.

Do not expose settings whose application path or supported range has not been established.

### Option table

| Key | Category | Stored values | Default | Applies |
| --- | --- | --- | --- | --- |
| `pcsx2x6_bios` | System | `auto`, BIOS filenames found in `<system>/pcsx2x6/bios/` | `auto` | Next content load |
| `pcsx2x6_region_check_bypass` | System | `enabled`, `disabled` | `enabled` | Next content load |
| `pcsx2x6_mtvu` | System | `auto`, `enabled`, `disabled` | `auto` | Next content load |
| `pcsx2x6_upscale` | Video | `1`, `2`, `3`, `4` | `1` | Next content load |
| `pcsx2x6_volume` | Audio | `0` to `200` in steps of 10 | `100` | Immediately |

- The interface follows `GET_CORE_OPTIONS_VERSION`: v2 registers with `SET_CORE_OPTIONS_V2_INTL` and categories, v1 with `SET_CORE_OPTIONS_INTL`, and anything else with `SET_VARIABLES`. A failed registration call does not select another interface. Simplified Chinese is provided when the frontend language is Simplified Chinese; every other language uses English.
- Numeric and enumerated options accept the listed stored values and fall back to their defaults for invalid values. `auto` for MTVU keeps the emulator's hardware-dependent choice. An explicitly selected BIOS that is missing or invalid causes content loading to fail with an error; it is not silently replaced by Automatic.
- Volume sets both SPU2 volumes on the CPU thread and applies them through SPU2's own configuration change, which keeps a muted output muted. It never reloads the settings, which would reset running state such as the Test DIP switch.
- A change to a load-time option while content runs is reported once per content session, compared with the values the content was loaded with.
- The internal resolution multiplier sets the maximum frame size to 1920×1080 times the multiplier. It is reported as the AV maximum before `retro_load_game` returns and restored to 1920×1080 when content fails to load or unloads. The GS may lower the multiplier from the device's texture size limit; the selected and effective multipliers are logged. An output image that cannot be allocated ends the session with an error. Memory use grows with the square of the multiplier and depends on the content; the core does not estimate it in advance.
- `pcsx2x6_renderer` is reserved for M5.5a and not registered while Vulkan is the only renderer.
- The display aspect ratio is not an option: the GS setting changes only the ratio reported to the frontend, which the frontend's own aspect setting already controls.

### Selected scope and validation

Keep the existing two-port RetroPad mapping and use the frontend's Controls/Remap facilities for host bindings. Verify a real frontend input path, independent player remaps, and saving/reloading a content-specific remap without applying it to unrelated content. Input injected inside the core can validate JVS behavior but cannot establish frontend remapping. Check controller choices and content-specific input descriptions; retain the existing English descriptions and upstream action names for this step.

| Boundary | Required behavior |
| --- | --- |
| Ordinary controls and drums | Directions, actions, Start and Service follow levels. Digital Don/Ka channels follow held levels; drum-mode D-pad hits do not also set joystick directions. Multiple mappings to one JVS bit are combined before updating it. |
| Coin and Test | Select inserts one coin per armed press into the corresponding player's slot. Only port 1 R3 toggles Test. Session start, successful reset and logical reconnect require a sampled release before these controls can trigger again. |
| Device changes | A disconnected port releases its controls when input is next applied. Disconnect/reconnect between requests, and device changes during explicit VM pause, remain visible to the next advancing request. Physical changes the frontend does not report cannot be treated as logical reconnects. |
| Pause | No frontend calls means no input sampling. Explicitly paused requests do not apply button levels or edges; pending device changes survive until resume. A previously sampled held Coin/Test does not repeat, but unobserved transitions during pause cannot be reconstructed. |
| Reset and reload | Successful reset clears mapped levels and disarms Coin/Test until a release is sampled; a refused reset leaves them unchanged. Held ordinary controls can apply again on the next advancing request. Preserve existing guest coin/DIP behavior. Known reset defects retain their limited validation boundary. |
| State loading | Define the input contract here and validate it in M5.4: restore guest coins, DIP and protocol state, clear old host-held levels, and require a sampled release before Coin/Test can trigger. Do not restore old physical-device assignments or frontend remaps. |

Use the existing fighting and digital-drum reference titles for short gameplay checks. Standard-layout bit checks, including overlapping direction/action mappings, are separate from real-game acceptance. A real standard-layout game requires its correct content and a bounded startup/input case; if no such case is available, retain the coverage gap and do not broaden the product's support claim. One tested standard title does not validate every layout.

Lightgun, wheel/pedals, touch and twin-stick remain deferred until a title and input device are selected. Investigate only integration failures found by the selected checks; protocol, layout or high-speed timing changes require separate scope review. Reuse unchanged evidence with its limits, document untested cases, and stop after normal shutdown once the required behavior is established. M5.3 may finish without input code changes if validation finds no integration defect; it does not depend on implementing save states early.

Input edges follow the states reported by the frontend. RetroArch menu transitions can report a release followed by a press even while the physical button stays held; release Coin and Test before returning from the menu to avoid another action. Content reload that unloads the core library does not establish resident-library lifecycle coverage, which remains in M5.5.

## M5.4 — Save-state implementation and validation

- [x] Implement synchronous in-memory `retro_serialize_size`, `retro_serialize` and `retro_unserialize` using the M5.1 design and any required focused state-completeness work. Meet libretro size/lifetime rules; report initialization requirements or other serialization quirks truthfully. The frontend owns slot naming and state-file storage.
- [x] At a safe frame boundary, synchronize the emulation workers and capture/restore guest state without serializing Vulkan handles, host pointers or open file handles. After load, invalidate stale output/audio, restore guest timing and arrange fresh output without an unrequested emulated frame; reconcile frontend AV information and host input edges.
- [x] Validate payload bounds, format, content/BIOS identity and relevant settings before mutating the VM. If restoration fails after mutation, terminate the affected session with an actionable error and suppress SRAM/NVRAM writeback from that failed restoration. Do not create a VM backup or attempt rollback, or continue with partially restored state.
- [x] Validate save/advance/load/replay for the selected System246 and System256 cases, repeated loads, paused operations, invalid/truncated/incompatible data and normal close/reopen. Compare agreed image, audio, progress and device-state checkpoints with known time-dependent inputs controlled.

Validated coverage is RetroArch 1.22.2 with the System246 and System256 reference titles: ordinary manual, paused, undo and automatic save and load, close and reopen, rejection of mismatched data and settings, and failure handling after restore mutation. Rejection while a memory-card command is busy is established by source review only. Other frontends, cross-build or cross-setting loading, and the frontend calling pattern of querying the size once and saving several frames later remain outside the validated scope.

Persistence follows the existing write paths. Restore SRAM in memory and persist the resulting branch on normal shutdown, retaining the current session's write protection and destination. State loading does not roll back save-card, dongle or BIOS companion files: record their content fingerprints and reject a mismatch before mutating the VM. Subsequent normal writes continue through the existing backends. Save-state operations add no file or VM backups and perform no rollback. Existing write protection, busy checks and temporary-file replacement remain in place. Never restore host handles from a previous session. First-version compatibility may be restricted to a defined build/format and configuration; ordinary same-session loading alone does not establish cross-session support.

### Accepted save-state design

- Use a core-owned, uncompressed in-memory container with format/build identity, content/BIOS/configuration identity, a segment table, bounded lengths and per-segment CRCs. Validate fixed sizes and variable-size limits separately; CRCs do not replace structural checks. Do not use the desktop ZIP loader's partial-read or reset-on-error behavior.
- Refactor the shared state-buffer access to support both growable desktop storage and fixed frontend-owned spans. Route reads, writes, block access and nested streams through checked accessors. Preserve the desktop format and include its path in regression checks.
- Process both save and load requests outside `VMManager::Execute()`, after the current event has completed and execution has exited safely. Use explicit request acknowledgements, not a blocking callback that jumps over its completion signal. First-frame and paused requests use the same outer boundary. Preserve the prior Running/Paused state and wait for a fresh frame grant before executing again.
- Complete the missing arcade-device and persistent card-protocol state, and retain the PAD segment. Exclude disabled USB, achievements and HostFS paths with explicit configuration checks. Guest state, current host input and frontend bookkeeping remain distinct.
- On the GS worker, flush pending draws, read back the texture cache and freeze the guest GS state. This user-triggered operation does not restore ordinary per-frame display readback. Restore VU memory and registers before rebuilding MTVU; defer its queued writes until the state is restored, then wait for VU and GS completion before reporting success.
- Restore the SPU2 partially filled output block and DC-filter history, discard obsolete core-owned output/audio, rearm host input edges and reconcile AV changes against what the frontend has accepted. The current SPU2 path submits full blocks with `AudioStream::WriteChunk`; its partial block lives in SPU2 rather than the generic stream staging buffer. Do not restore Vulkan objects, frontend request counters or already delivered audio. A paused load redraws without emulation advance, or shows black until a valid image exists.
- Report the actual length of the current state and declare `MUST_INITIALIZE | CORE_VARIABLE_SIZE`. EE, IOP and arcade RAM are saved as a page bitmap followed by their non-zero 4 KiB pages; loading clears omitted pages. Other segments keep their existing representation, and internal structures are stored at their actual length. Validate every segment against limits derived from maximum capacities, not one observed snapshot. The container format version is checked independently of build identity.
- Measure once per state generation, which changes on every completed frame, successful load, completed reset and session start or end; repeated size queries reuse that measurement. A save into a buffer smaller than the current state fails without writing. Loads check the supplied data by its own length and structure. RetroArch 1.22.2 does not acknowledge variable sizes; its ordinary manual, undo and automatic save paths query the size immediately before saving, and only those paths are covered. Validate initialization and zero-frame requests separately; account for frontend undo buffers when measuring peak memory.
- Mark persistence untrusted before the first restore mutation. Clear that guard only after the complete restore, worker reconstruction and synchronization succeed. On a later failure, the CPU worker reports a terminal result without advancing; the frontend performs cleanup and error callbacks, skipping SRAM/NVRAM writeback from the untrusted state. Normal successful-load shutdown retains the persistence policy above. Existing card/dongle writes are not rolled back.

The initial format targets the same build, content, compatible configuration and backend, including close/reopen. Non-normal savestate contexts and unsupported configurations are rejected. The core information file declares save states with `savestate_features = "basic"`, so frontends that honor it keep rewind, run-ahead and netplay unavailable.

Save states do not automatically establish rewind, runahead or netplay support. Assess determinism, repeated serialization cost and memory requirements separately before advertising these features.

### Native reuse and implementation order

PCSX2x6 already implements save states. Reuse its [state components and load preparation](https://github.com/PS2Homebrew-arcade/pcsx2x6/blob/583f0e90907d69bb2db670f570d0865260fcc71b/pcsx2/SaveState.cpp), including CPU/IOP internals, memory entries, SPU2, PAD, GS and cache/TLB reconstruction. Its desktop workflow also manages filenames, screenshots, optional backups and ZIP compression; those file operations are separate from the synchronous memory interface owned by libretro. Reusing the state engine does not require desktop ZIP compatibility or retaining its partial-read and reset-on-error policies. Preserve the existing desktop format when adapting shared buffer access.

1. Establish the native reference behavior and component contracts. Define maximum sizes and non-mutating validation, add missing arcade/card/output state, and adapt bounded storage and deferred MTVU reconstruction. Check shared desktop callers as well as component round trips before exposing callbacks.
2. Implement acknowledged save/load requests at the outer execution boundary, including GS readback, worker synchronization, output/input cleanup and failed-restore persistence protection. Validate short deterministic replay and controlled failures through diagnostic entry points.
3. Connect synchronous libretro callbacks, actual-length states and serialization quirks. Check frontend undo-save behavior, manual/automatic/paused operations, and loading after normal content close/reopen. Treat zero-run requests separately from automatic loading observed after a run has started.
4. Validate an identified final build before enabling save-state metadata. Record state length, operation latency and peak memory, including frontend-owned buffers; retain explicit unsupported cases. Reuse unchanged evidence instead of repeating unrelated gameplay or treating ordinary content reload as resident-library lifecycle coverage.

## M5.5 — Lifecycle and failure handling

- [x] Cover content changes, recovery from a start failure after the GS opens, reinitialization within a resident DLL, and direct `retro_deinit` with an active VM through real Vulkan negotiation. Ordinary RetroArch content reload does not cover resident-library reinitialization or direct deinitialization.
- [x] Check affected pause, shutdown, content reload and cached-context paths. Retain existing input, audio, save-state and reset evidence where those paths are unchanged, including the documented reset limits.
- [x] Review known issues individually. Investigating the emulator reset failure and post-reset audio requires separately scoped emulator work; neither save-state loading nor content reload is an implicit replacement for `retro_reset`.

Frontends must call `retro_deinit` before unloading the library. If deinitializing an active session without first calling `context_destroy`, keep the frontend-owned Vulkan device and interface valid until deinitialization returns. The core stops its workers and clears its stored interface reference; device and instance ownership remains with the frontend. Do not invoke callbacks from the ended session after deinitialization.

On Windows, process-termination detach releases the CPU/GS thread handles left by an exit without deinitialization. This does not perform normal shutdown or guarantee persistent-data writes. Ordinary library unloading retains the requirement to stop and join the core's workers first.

**Acceptance:** the selected lifecycle cases terminate safely and preserve writable data. Unverified cases and unresolved issues remain explicit; a successful integration check does not establish that the underlying emulator reset defect is fixed.

## M5.5a — Additional rendering backends and renderer selection

The Windows core supports Vulkan and Direct3D 11 through the Renderer option. Vulkan remains the default and changes take effect when content is closed and loaded again. D3D12 and OpenGL remain candidates for separately scoped integration. Software rendering and paraLLEl-GS are separate renderer choices, not interchangeable graphics API backends.

- [x] Probe the render-interface versions and context-negotiation support actually returned by the target RetroArch 1.22.2 binary, recording these as separate interface contracts. Compare D3D11, D3D12 and OpenGL under the same frontend and independent-GS-worker constraints. A renderer enum or binary string search alone does not establish interface support.
- [x] Select the first backend from that comparison, with a demonstrated hardware-image handoff. Check the existing GS implementation and build dependencies, and define device/context ownership, thread access, synchronization, resource reuse, startup, destruction and cached-context behavior before implementation.
- [x] Implement and validate that complete path, preserving the frame/input/audio contract. Hardware paths should deliver images through their matching frontend interface rather than recreate ordinary per-frame CPU readback. Keep backend-specific lifetime rules distinct; do not assume Vulkan queue/index rules apply to D3D or OpenGL.
- [x] Complete the localized renderer core option prepared in M5.2: Vulkan remains the default, changes apply on close/reload, and unavailable backends are not offered. Define any future Automatic/fallback behavior explicitly; the first additional backend does not imply live API switching or a software fallback.
- [x] Check both reference titles for startup, output/AV correctness, audio/input, pause, fullscreen/context handling, close/reopen and actionable failure cleanup. Validate state loading within each supported backend; reject cross-backend states until compatibility is established. Update runtime requirements and metadata only when the new path is implemented and accepted.

Direct3D 11 was selected as the first additional backend. With RetroArch 1.22.2, D3D11 and D3D12 provide only their v1 render interfaces after the frontend creates its own device; no D3D context negotiation exists in the standard interface. RetroArch keeps its D3D11 device when it recreates the video driver, whereas its D3D12 driver creates a new device each time.

The D3D11 path keeps the independent GS worker. The GS creates its own D3D11 device on the frontend's adapter, identified by its LUID, and renders each image into one of two keyed-mutex shared textures. The frontend side opens them on the frontend's device and presents them through pixel shader slot 0, as the v1 interface requires. Each side owns a texture only after a successful acquire and releases only what it owns. A new image size creates a new texture set that the frontend takes over before presenting. The previous set is destroyed only after the frontend has released it. A repeated `context_reset` on the same device keeps the held image; another device is not supported and ends the content. Context destruction, deinitialization and failures release the frontend side before the GS closes. Vulkan behavior is unchanged.

States load only within the backend that saved them. When RetroArch recreates its video driver while paused, both backends show black until the content runs again: RetroArch repeats a paused frame from its own texture, which it recreates with the driver.
