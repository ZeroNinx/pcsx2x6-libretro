# M5 — Core Features and Compatibility

Status: M5.1 capability audit and save-state design are complete; functional implementation has not started. The accepted starting implementation is `d477509`, with direct Vulkan-image delivery and an independent GS worker. Runtime requirements remain Vulkan context negotiation v2 with no software-video fallback.

## Goal and priorities

Complete the everyday libretro core experience: truthful capability information, save states, useful and localized core options, reliable input, and predictable lifecycle and persistent storage. Preserve the accepted frame/input/audio contract and keep emulation fixes distinct from frontend integration.

The original performance, board/media, platform, VFS and peripheral candidates remain available, but do not all become requirements for M5. Core features take priority. Additional renderer/backend support is selected for M5.5a, with its option contract prepared in M5.2; other original candidates remain individually scoped. Each implementation step receives a bounded design and acceptance case before code changes; the outline below does not authorize bulk porting reference implementations.

## M5.1 — Capability and state-completeness audit

- [x] Inventory implemented, missing and conditional libretro capabilities against the exported callbacks, core-info file, README and package. Correct contradictory capability descriptions when implementing the inventory changes.
- [x] Audit the existing state entries and their restore paths: CPU/IOP/VU, GS, SPU2, arcade RAM/SRAM, JVS/UART, ATA/ATAPI and media position, timers/interrupts, cards, BIOS-side state and integration-owned state. Identify omitted mutable state and how each item is restored or deliberately external to a snapshot.
- [x] Define the first save-state support boundary, format/version and content/configuration identity checks, memory budget, stable serialization size policy and CPU/GS/MTVU quiescence protocol. Decide how restoring in-memory saves interacts with later disk persistence before implementation.

The current libretro serialization callbacks are stubs. The emulator already has ACRAM, SRAM and JVS state entries, but its JVS entry stores coin counts only; existing state functions do not establish complete arcade-device coverage. Reuse valid components rather than treating a wrapper around the desktop file-save API as sufficient.

The initial target is loading within the same build, content and compatible configuration, including after closing and reopening content. A same-session-only restriction requires an explicit scope review. Define refusal conditions during startup, shutdown and unsafe card/media writes.

**Deliverable:** a capability matrix and the save-state design below, with explicit gaps and acceptance cases. Implementation and runtime acceptance remain in M5.4. Unresolved state completeness blocks advertising save states, not unrelated option or input work.

## M5.2 — Core options and localization

- [ ] Establish a maintained option table: stable keys and values, categories, defaults, validation, supported frontend option interfaces and application timing (live or next content load). Preserve Automatic BIOS selection and default-enabled Region Check Bypass.
- [ ] Select a small first set of useful settings. Start with the existing BIOS/patch controls and output volume; evaluate display aspect and internal resolution only with an explicit image-size/resource budget and validated GS update path. Keep Vulkan as the implemented backend and default until M5.5a validates another path. Define the renderer option as requiring content reload; expose only implemented, validated values, with the same English/Simplified Chinese treatment as other options. Exposing MTVU is a usability decision, not a claim of a performance improvement.
- [ ] Provide English and Simplified Chinese labels and help, with English fallback. Translate presentation text without changing stored keys/values, BIOS filenames or patch identifiers. Route live changes through the owning thread and avoid resetting Test DIP or unrelated input state through blanket settings reloads.

**Acceptance:** defaults preserve existing behavior; frontend language selection, saved options and content overrides work; live changes apply safely; restart-required changes are clearly labelled and take effect on reload. Do not expose settings whose application path or supported range has not been established.

## M5.3 — Input completeness

- [ ] Verify frontend remapping, P1/P2 isolation, descriptors and controller-device changes for the supported fighting, standard and digital drum layouts. Reuse frontend remapping instead of adding a second host-device binding system.
- [ ] Define coverage for ordinary actions, directions, Coin, Start, Service, Test, held levels and reconnect/reset/state-load edges. Preserve the distinction between digital drum levels and physical hit timing.
- [ ] Select additional input modes only against an identified game and device: lightgun, steering/pedals, touch or twin-stick. Each needs its own mapping, calibration/range rules and bounded comparison before implementation.

ISSUE-001 remains a separate timing investigation. Ordinary input integration does not establish high-speed chart accuracy, and the milestone does not assume that a threading change fixes it.

## M5.4 — Save-state implementation and validation

- [ ] Implement synchronous in-memory `retro_serialize_size`, `retro_serialize` and `retro_unserialize` using the M5.1 design and any required focused state-completeness work. Meet libretro size/lifetime rules; report initialization requirements or other serialization quirks truthfully. The frontend owns slot naming and state-file storage.
- [ ] At a safe frame boundary, synchronize the emulation workers and capture/restore guest state without serializing Vulkan handles, host pointers or open file handles. After load, invalidate stale output/audio, restore guest timing and arrange fresh output without an unrequested emulated frame; reconcile frontend AV information and host input edges.
- [ ] Validate payload bounds, format, content/BIOS identity and relevant settings before mutating the VM. If restoration fails after mutation, terminate the affected session with an actionable error and suppress SRAM/NVRAM writeback from that failed restoration. Do not create a VM backup or attempt rollback, or continue with partially restored state.
- [ ] Validate save/advance/load/replay for the selected System246 and System256 cases, repeated loads, paused operations, invalid/truncated/incompatible data and normal close/reopen. Compare agreed image, audio, progress and device-state checkpoints with known time-dependent inputs controlled.

Persistence follows the existing write paths. Restore SRAM in memory and persist the resulting branch on normal shutdown, retaining the current session's write protection and destination. State loading does not roll back save-card, dongle or BIOS companion files: record their content fingerprints and reject a mismatch before mutating the VM. Subsequent normal writes continue through the existing backends. Save-state operations add no file or VM backups and perform no rollback. Existing write protection, busy checks and temporary-file replacement remain in place. Never restore host handles from a previous session. First-version compatibility may be restricted to a defined build/format and configuration; ordinary same-session loading alone does not establish cross-session support.

### Accepted save-state design

- Use a core-owned, uncompressed in-memory container with format/build identity, content/BIOS/configuration identity, a segment table, bounded lengths and per-segment CRCs. Validate fixed sizes and variable-size limits separately; CRCs do not replace structural checks. Do not use the desktop ZIP loader's partial-read or reset-on-error behavior.
- Refactor the shared state-buffer access to support both growable desktop storage and fixed frontend-owned spans. Route reads, writes, block access and nested streams through checked accessors. Preserve the desktop format and include its path in regression checks.
- Process both save and load requests outside `VMManager::Execute()`, after the current event has completed and execution has exited safely. Use explicit request acknowledgements, not a blocking callback that jumps over its completion signal. First-frame and paused requests use the same outer boundary. Preserve the prior Running/Paused state and wait for a fresh frame grant before executing again.
- Complete the missing arcade-device and persistent card-protocol state, and retain the PAD segment. Exclude disabled USB, achievements and HostFS paths with explicit configuration checks. Guest state, current host input and frontend bookkeeping remain distinct.
- On the GS worker, flush pending draws, read back the texture cache and freeze the guest GS state. This user-triggered operation does not restore ordinary per-frame display readback. Restore VU memory and registers before rebuilding MTVU; defer its queued writes until the state is restored, then wait for VU and GS completion before reporting success.
- Restore the partially filled audio block, discard obsolete core-owned output/audio, rearm host input edges and reconcile AV changes against what the frontend has accepted. Do not restore Vulkan objects, frontend request counters or already delivered audio. A paused load redraws without emulation advance, or shows black until a valid image exists.
- Report one bounded maximum size per initialized content session and declare `MUST_INITIALIZE`. Derive variable-segment limits from their maximum capacities, not one observed snapshot. Validate initialization and zero-frame requests separately; account for frontend undo buffers when measuring peak memory.
- Mark persistence untrusted before the first restore mutation. Clear that guard only after the complete restore, worker reconstruction and synchronization succeed. On a later failure, the CPU worker reports a terminal result without advancing; the frontend performs cleanup and error callbacks, skipping SRAM/NVRAM writeback from the untrusted state. Normal successful-load shutdown retains the persistence policy above. Existing card/dongle writes are not rolled back.

The initial format targets the same build, content, compatible configuration and backend, including close/reopen. Non-normal savestate contexts and unsupported configurations are rejected. Keep save-state availability disabled in metadata until M5.4 validation passes, including post-SRAM failure injection and MTVU memory/program restoration.

Save states do not automatically establish rewind, runahead or netplay support. Assess determinism, repeated serialization cost and memory requirements separately before advertising these features.

## M5.5 — Lifecycle and failure handling

- [ ] Cover reinitialization within a resident DLL and direct `retro_deinit` with an active VM using a host that can exercise the Vulkan negotiation path; ordinary RetroArch content reload does not cover either case. Choose the smallest suitable validation mechanism before building a new host.
- [ ] Recheck pause, reset dispatch/refusal, shutdown, content reload and cached-context recreation after the selected feature changes. Keep audio bounded, do not replay stale frames/audio, and retain source/save isolation.
- [ ] Review known issues individually. Investigating the emulator reset failure and post-reset audio requires separately scoped emulator work; neither save-state loading nor content reload is an implicit replacement for `retro_reset`.

**Acceptance:** the selected lifecycle cases terminate safely and preserve writable data. Unverified cases and unresolved issues remain explicit; a successful integration check does not establish that the underlying emulator reset defect is fixed.

## M5.5a — Additional rendering backends and renderer selection

This is a selected feature workstream, following the state/lifecycle work above. The target is Vulkan plus an additional validated hardware backend, not every renderer supported by the emulation base. Compare D3D11, D3D12 and OpenGL against the supported frontend before selecting the first Windows backend; no API has priority before interface feasibility is established. Software rendering and paraLLEl-GS are separate renderer choices, not interchangeable graphics API backends.

- [ ] Probe the render-interface versions and context-negotiation support actually returned by the target RetroArch 1.22.2 binary, recording these as separate interface contracts. Compare D3D11, D3D12 and OpenGL under the same frontend and independent-GS-worker constraints. A renderer enum or binary string search alone does not establish interface support.
- [ ] Select the first backend from that comparison, with a demonstrated hardware-image handoff. Check the existing GS implementation and build dependencies, and define device/context ownership, thread access, synchronization, resource reuse, startup, destruction and cached-context behavior before implementation.
- [ ] Implement and validate that complete path, preserving the frame/input/audio contract. Hardware paths should deliver images through their matching frontend interface rather than recreate ordinary per-frame CPU readback. Keep backend-specific lifetime rules distinct; do not assume Vulkan queue/index rules apply to D3D or OpenGL.
- [ ] Complete the localized renderer core option prepared in M5.2: Vulkan remains the default, changes apply on close/reload, and unavailable backends are not offered. Define any future Automatic/fallback behavior explicitly; the first additional backend does not imply live API switching or a software fallback.
- [ ] Check both reference titles for startup, output/AV correctness, audio/input, pause, fullscreen/context handling, close/reopen and actionable failure cleanup. Validate state loading within each supported backend; reject cross-backend states until compatibility is established. Update runtime requirements and metadata only when the new path is implemented and accepted.

The published RetroArch v1.22.2 [D3D11 interface](https://github.com/libretro/RetroArch/blob/v1.22.2/libretro-common/include/libretro_d3d11.h) is version 1 and has no context-lock or sync-index callbacks. The reference D3D11 path attempts to negotiate its extended v2 interface but also accepts v1; the extended context-lock and sync-index protocol cannot be assumed on its v1 path or in the target frontend. A D3D11 v1 path needs a demonstrated context-ownership and image-handoff protocol compatible with the independent GS worker; the absence of a lock callback alone does not establish that moving GS consumption is necessary or safe. The [D3D12 v1 interface](https://github.com/libretro/RetroArch/blob/v1.22.2/libretro-common/include/libretro_d3d12.h) exposes a command queue, required resource state and texture handoff, but completion and texture-reuse rules still require validation. OpenGL similarly requires an explicit current-context, sharing and thread-ownership design.

Using a frontend that implements additional interface versions would change the runtime requirements and needs a separate scope decision. Do not make a customized frontend an implicit prerequisite.

The accepted starting core still requires Vulkan negotiation v2. If the selected additional path cannot satisfy the lifecycle or image contract, review its scope explicitly before milestone completion rather than exposing a nonfunctional option.

## M5.6 — Evaluate the original candidate workstreams

| Workstream | Entry condition and decision |
| --- | --- |
| CPU/GS/MTVU and timer behavior | New cost evidence and a matched workload. Preserve M4 decisions; do not repeat rejected experiments without a changed hypothesis. |
| Additional graphics backends | Selected as M5.5a for the current Windows target; begin with one additional hardware path and expose it only after end-to-end validation. Other backends remain individually scoped. |
| System256/Super256, additional games and CD/DVD/HDD arrangements | One named board/media/game case and a standalone reference. Existing System256 coverage is limited, not absent. |
| ARM64 and other platforms/frontends | A named target, toolchain, dependencies and validation device. Keep architecture porting separate from feature work. |
| VFS and resource packaging | Audit actual file access and the target's path/URI requirements before choosing VFS coverage; an isolated manifest reader is not full media VFS support. |
| Additional arcade peripherals | Use the M5.3 per-game/device entry condition; do not promise all emulated JVS modes. |
| Memory exposure, cheats, disk control, achievements and no-content startup | Assess actual product use and interface semantics first. Directly persisted SRAM must not acquire a competing frontend save writer; fixed arcade media must not gain fictitious disc switching. Leave unsupported APIs truthful. |

Record each candidate as selected, deferred or rejected with a short reason. Only selected work receives a detailed TODO and implementation scope.

## M5.7 — Acceptance and distribution

- [ ] Run affected checks on an identified final build, distinguishing uninstrumented frontend checks from controlled fault/input builds. Reuse unchanged evidence with its limits; add checks for changed settings, serialization, input, persistence, lifecycle and selected renderer/backend paths.
- [ ] Update core-info metadata, README, option documentation, known issues and packaging to match implemented capabilities and requirements. Include the localized option data and corresponding source/license materials. Keep test content and user firmware outside the package.
- [ ] Freeze the accepted binary, source/configuration identity and comparison artifacts. Confirm completion of the selected feature scope and explicitly review any deferred save-state or lifecycle requirement before declaring M5 complete.

M5 promises the selected core-feature scope, not all optional compatibility and performance workstreams. User-visible availability follows verified behavior; no feature is advertised solely because its API callback exists.
